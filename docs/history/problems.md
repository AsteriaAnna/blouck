#### 0.6.1 MD 文档的真正结构

现状：`nodes.free_md`、`edges.md`、`buildings.md` 都是**单个 TEXT blob**，节点另有 definition/aliases 等字段，但没有“人读的 MD”和“机器可校验的结构”之间的分层；也没有版本/来源引用规范。

建议结构（草案，待确认）：**结构化字段负责机器读写与校验，MD 正文负责人读与编辑，两者通过 ID 双向引用**。

| 对象 | 结构化字段（DB） | MD 正文结构（frontmatter + 固定小节） | 自动/用户 |
|---|---|---|---|
| 节点 | id/name/type/definition/aliases/source_span_ids[]/tier/status | `定义`（自动）/`我的理解`（用户）/`证据与来源`（自动列引用）/`相关关系`（自动生成列表）/`待探索`（用户/系统）/`外部资料`（用户） | 混合 |
| 正式关系 | src/dst/predicate/label/evidence_span_id/confidence/origin/claim_status/updated_at | `语义`（谓词+A→B方向）/`成立依据`（证据原句）/`边界与反例`/`我的备注`/`来源轮次` | 依据自动，备注用户 |
| 探索来源线 | src/dst/source_span_id/round/trigger（voice/text/manual）/created_at | `来源原句`/`触发方式`/`轮次与时间`/`A→B`/`可跳转`（只读凭证） | 自动 |
| 虚线建议 | src/dst/predicate_guess/evidence/confidence/reason | `建议卡`（AI 依据/置信度/建议谓词/接受/忽略），不是完整 MD | 自动 |
| 方向线 | node_id/question/reason/angle/target_hint/status/round | `方向卡`（问题/理由/可能指向/去探索/忽略），**无 MD** | 自动 |
| 副本 | kind/anchor/steps/status/md | `背景`/`规则`/`步骤`/`来源` | 混合 |

- 原则：**MD 不是数据库**（查询/校验/去重靠结构化字段）；MD 提供可 diff、可渲染、可分享的内容。
- 引用：来源用 blockquote + source_span_id；关系/节点用 ID 链接（未来可做 backlink），避免标题改名失效。
- 版本：MD 正文建议加 `updated_at/revision`（用户编辑乐观锁），与结构化字段同事务。
- 兼容：现有 `free_md` 作为“节点 MD 正文”迁移，不推翻现有字段。

#### 0.6.2 LLM 如何识别关系，以及怎么判断“真正有意义”

**核心判断（第一性原理）**：一条有意义的线 = **一个在给定本体下成立、且被原文证据蕴含的 A–P–B 命题**；不是“两个概念在同一段文本里出现/语义相近”。

抽取与校验要分成**生成器**和**校验器**两段（避免同一个 LLM 自说自话）：

```text
文本/语音片段
 → ① 候选生成（LLM，受控 schema）
     entities[]（名词概念，类型）+ relations[]{src,dst,predicate(受控词表),evidence(原文子串),confidence}
 → ② 证据接地：evidence 必须是原文子串/近子串（忽略标点空白），否则丢弃
 → ③ 语义蕴含校验：evidence 是否“蕴含”这条 A–P–B（NLI/事实核查模型；不要只做 embedding 相似）
 → ④ 本体/规则约束：predicate 的 domain/range/方向/基数/冲突（同 pair 反向同谓词、矛盾关系、最多谓词数）
 → ⑤ 反例与自洽检查：LLM 反方问一次（“这条关系是否只是共现/是否方向错”），多采样投票
 → ⑥ 置信度打分 + 分档：
      high → 正式关系（formal，可自动）
      mid  → 虚线建议（suggest，用户接受）
      low/失败 → 不落图（只进日志/候选池）
 → ⑦ 用户确认 / 编辑（accept 时保留用户内容；语音自动 commit 是否算“确认”待 D6）
```

- **meaningfulness 的四道门**：G1 证据接地（有原文句）、G2 语义蕴含（句子确实支持这条关系）、G3 本体约束（类型/方向合法、不矛盾）、G4 产品确认（高置信自动/中置信建议/低置信拒绝）。
- **LLM 的角色**：生成候选 + 解释；**不是**唯一裁判。校验器可用更小/更专的模型（NLI/事实核查）与规则引擎，成本可控、可解释。
- **反“胡乱关联”**：① 只共现不判关系；② 同 pair 反向/矛盾检测；③ 谓词白名单与定义；④ 证据必须逐字可查；⑤ 低置信只能进建议线；⑥ 人工抽检 + 负例集（共现但无关系、方向反、错误谓词）。
- **评测**：gold triples 的 P/R/F1 + 证据覆盖率 + 方向准确率 + 负例误报率 + 人工 meaningfulness 抽检；现有 `server/eval` 只有 12 例、mapType 91.3%、方向命中 1/5（2026-11-14），需要扩集与加负例。

#### 0.6.3 点击“关联/探索点/探索线”之后出现什么

| 点击对象 | 面板内容 | 动作 |
|---|---|---|
| 正式关系 | 关系卡：谓词+方向、证据原句、建立方式（AI/手动）、来源轮次、关系 MD（用户可编辑）、备注 | 编辑/保存；**不可删除**（按设计；修正路径待 D8） |
| 探索来源线 | 来源卡：A→B、来源原句、触发方式（语音/文字/手动）、轮次/时间、跳转两端 | 只读；可“从这条来路继续探索” |
| 虚线建议 | 建议卡：AI 依据/置信度/建议谓词、**接受/忽略** | 接受→转正式（名称去问号、名称淡入）；忽略→归档（待定） |
| 方向线/问号点 | 方向卡：问题、理由、**可能指向（已有节点/新方向）**、「去探索」「换个方向」「忽略」 | 去探索→触发新一轮抽取（见 0.6.4） |
| 节点 | 节点抽屉（已有）：档位/自由区/题目区/关系/方向 | 维持现有，补“探索”入口与 4 方向展示 |

#### 0.6.4 探索型节点（每个节点 4 个）与探索链路

> 新增约束：每个节点保证 4 个探索型节点/方向。当前实现是“方向边最多 2 条、只有 frontier 渲染”，需要改（技术类任务）。

**（a）探索方向怎么来：语义 + 图结构 + 关系推断，三层混合，不单靠语义**

1. **语义层（LLM）**：基于节点 definition/free_md/邻居，生成“还没有被覆盖的探索角度”的问题句；角度来自谓词/知识类型体系（定义、上位、组成、前置、对比、替代、指标、应用、边界、反例…）。
2. **图结构层（规则/图算法）**：检查当前节点的关系缺口——有 partOf 子节点但没上位 → 补“上位/归类”；没有 prerequisite → 补“前置/依赖”；没有 contrast → 补“对比”；没有指标/应用 → 补对应角度；结合 frontier/邻居（“Look before you hop”式下一跳/上下文扩展）。
3. **用户/系统层**：节点 MD 的“待探索”区、历史未消费方向、低置信建议/争议关系 → 转成探索方向（优先级更高）。

生成流程：候选（LLM 6–8 条 + 缺口模板）→ 去重（embedding 相似度 + 角度分类）→ 覆盖度/新颖度/可回答性打分 → **取 4 条**；每条含 `question/angle/reason/target_hint/status`；不足 4 条时用模板兜底，必须保证 4 条。消费/新增关系/编辑 MD 后重算，保留历史（consumed）避免重复问。

**（b）点击探索线以后：连接已有节点，还是生成新节点？**

- 默认**先打开方向卡，不直接落图**；点“去探索”才执行抽取。
- 抽取前先做“已有节点匹配”（名称/别名/语义检索）：
  - 若高置信命中已有节点 → 优先**连接已有节点**（生成来源线/建议关系，不重复建节点），方向卡上直接显示“可能指向：X”；
  - 若没有命中 → **生成 1–3 个新节点候选**（带证据），校验通过后落图；
- 即：**“优先连已有，否则生成新”**；当前实现是每次 `/extract` 生成新节点（同名靠 findNode 去重），没有显式“连已有”分支。

**（c）新节点之后怎么连、怎么再生成探索线**

1. 新节点 B 必须有一条**探索来源线 A→B**（来源原句/问题/轮次/触发方式），保证“来路可追溯”；
2. 抽取出的**正式/建议关系**同时落库（如 kindOf/partOf 等，带证据、过校验；低置信为建议线）；
3. **B 也生成自己的 4 个探索方向**（每个节点保证 4 个）；A 被消费的方向 `open→consumed` 并补新方向；
4. 全局去重：新方向与已有方向/已消费方向语义相似度超阈值的不再生成；避免“A 探索到 B、B 又探索回 A”的死循环（可生成但需标记“已访问”，待定）；
5. 失败/无结果：保留方向线（不消费），提示“这个方向暂时没有可靠内容”；重复探索：提示已探索过并给历史结果。

**状态机（草案）**

```text
方向线 open
  --点击--> 方向卡（不改变状态）
  --去探索--> exploring
      --有可靠结果--> consumed（消失/归档）+ 生成 来源线/建议/正式 + B 的 4 方向 + A 补方向
      --无可靠结果--> open（保留）
      --用户取消--> open
  --忽略--> archived（可撤回）
建议线 suggest
  --接受--> formal（名称去问号、名称淡入、用户编辑保留）
  --忽略--> archived（待定）
来源线 source：只读凭证，不参与 accept；不可删除（待定）
正式关系 formal：不可删除（设计）；修正/否定/归档待 D8
```

### 1. 背景梳理：四类线的设计期望、负责业务与现状对比

| 线型 | 当时设计它的期望 | 它负责的业务/用户动作 | 目前情况（实现事实） | 差距性质 |
|---|---|---|---|---|
| **正式关系** | 表示“已建立的知识连接”，稳定、可追溯、不可删除 | 看懂知识结构；补依据/备注；作为后续推理的地基 | 有数据（kind=formal，label/evidence 可存），但**看不到名称/说明、点不开**；MD 字段无人可达；不可删除（符合设计） | 设计只写了“不可删除”，没写“可查看/可说明”；实现也没做 → **两边都缺** |
| **探索来源关系** | 回答“这轮从哪探索到哪”，是正式关系的一种、可追溯 | 追溯节点/关系的来源原文与轮次；复盘学习路径 | 有 source 边（label 固定「本轮探索来源」），**无起点圆点、无标签、不可点**；节点抽屉不展示；无 A→B/原句展示 | 设计写了语义与视觉；实现没做；**来源内容模型未定义** |
| **虚线建议** | “AI 建议、用户可接受”，≠已建立关系；确认过程可见 | 审核 AI 连接；接受后变成正式关系 | 有 suggest 边、可点开、可接受；**接受后路牌/名称消失，无“名称淡入”**；语音提交会批量自动转 formal（用户未确认）；先编辑再接受会被覆盖 | 设计写了“用户可接受/看见确认”；实现部分做、部分违背；**自动确认是否合法未定义** |
| **方向线** | “下一步探索方向”，无 MD；问号光点点开提示方向问题 | 指路/触发探索；探索完成后消失或留痕 | 有 direction 边+路牌；点开有方向卡+探索按钮；确认后消费并跑 `/extract`；**方向线不会“变成”另一种线**；只有 frontier、每节点最多 2 条；与建议同为虚线风格 | 设计只到“提示方向问题”；**点击后的生命周期未定义**；4 方向/视觉区分未实现 |

**一句话**：设计覆盖了“线型语义 + 视觉一句话”，但**没覆盖“线的内容模型、点击行为、转换生命周期、测试”**；实现则在“数据层”走了很远、在“可读/可确认/可修正”上留了大洞。两边都不是“完善需求 vs 未实现”，而是**需求本身需要先补完**。

### 2. 任务梳理：下一步需要判断/完成什么

#### 2.1 待判断的设计决策（先于开发）

- **D1** 正式关系是否可点开？只读说明，还是可编辑 MD/名称？

- **D3** 来源线与正式关系是“同一条线的两种标签”还是“两条并存”？来源线可点/可删吗？
- **D4** 建议线：直接接受（现状）还是先看建议卡再接受？忽略/归档怎么处理？
- **D5** “每个节点 4 个探索方向”是硬约束吗？4 个角度如何定义/防重复？方向线点击后：消费消失/留痕/转来源线？
- **D6** 语音提交自动把建议转 formal 是否算“用户接受”？不允许的话，语音链路如何保留建议态/批量确认？
- **D7** 线宽/视觉以哪份为准（§3.5 细实线 vs §8.23 管状较粗）？四类线在 3D 里怎么呈现标签/悬停？
- **D8** “不可删除”下错误关系如何修正（否定/归档/存疑/允许删除）？
- **D9** 边 MD 与节点 MD 是否同一编辑器/同一内容模型？
- **D10** 线测试的验收口径（L1–L5 哪些进本轮）？

### 3. 资料调研（第一性原理 + 开源项目/参考）

> 检索时间 2026-11-16；GitHub 直连抓取受限，以下按公开项目页/论文页记录**项目定位与可借鉴点**，链接保留供复核；未验证细节不作为结论。

#### 3.1 第一性原理拆解（先把问题还原成可验证的命题）

- **关系是什么**：一个可被证据支持的 A–P–B 命题（不是“两个词在同一段文本里”）；可附加本体约束、置信度、来源、时间。
- **“有意义”怎么判**：证据蕴含（entailment）+ 本体约束（domain/range/方向）+ 非平凡性（不是共现/同义）+ 一致性（不矛盾）+ 产品接受（用户确认/规则阈值）。
- **探索是什么**：在当前图/内容上识别“知识缺口”→ 生成候选方向 → 选择并执行 → 落图并留下来源凭证 → 再产生新缺口（闭环）。
- **MD 是什么**：人读/可 diff 的正文；与机器字段分离，用 ID 互链；版本与来源可追溯。
- **线型是什么**：知识连接的**状态**（建议/正式）与**类型**（关系/来源/方向），UI 要能一眼区分并支持对应动作。

#### 3.3 初判（供选型，不是结论）

- **可复用的**：GraphRAG/LightRAG 的“LLM 抽取 + 图结构/去重”思路；llm-graph-builder 的 schema 约束；Graphiti 的“关系会随时间失效/更新”；GLiNER-Relex/DeepKE 的轻量 RE 作为校验/兜底；MiniCheck/AlignScore 的蕴含校验思路；SHACL 的约束建模思路。
- **必须自研的**：线型语义/四类线生命周期、4 方向生成与刷新规则、关系 meaningfulness 判定阈值、用户确认/编辑仲裁、线的 UI 与 MD 内容模型（这些没有现成项目直接给）。
- **不建议**：直接引入 GraphRAG/LightRAG 作为主架构（它们是 RAG 检索框架，和“个人增量知识图 + 游戏化线型 UI”不是一回事）；引入 Neo4j/RDF 全栈（现有 SQLite 够用，约束可用代码实现）。
- **需要 PoC 验证的**：① DeepSeek 受控抽取 + 独立 NLI 校验在中文短句上的准确率/成本；② GLiNER-Relex 或小模型能否当“校验/兜底”；③ 4 方向生成的去重/覆盖效果；④ MD 结构（frontmatter/分节）在现有编辑器的迁移成本。

#### 3.4 检索局限

- 本次 GitHub 仓库页面抓取多次超时/失败，表中“定位”依据公开项目页/论文摘要/包索引等可见信息；**具体 API/许可/维护状态需要开发前二次核实**。
- 中文 NLI/关系校验模型、中文短句 RE 的开源选型，需要单独做一轮中文基准测试（现有 `server/eval` 的 12 例可扩展）。
