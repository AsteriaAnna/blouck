## 001 · 关系的实施方式

- 提出：2026-11-16
- 基线：语音/焦点/相机修复提交 `d768326` 之后的工作区（该轮只读审计，未改代码）
- 需求来源：**最初那份决策文档《知识世界 MVP：模型选型与「游戏感」落地建议》**（工作区根目录 `知识世界-MVP-模型与视觉决策建议.md`，不在本仓库内）。本文第 1 节以它的「线的类型」和交互期望为口径。
- 实现承诺来源：`03-implemented.md` §7（关系当前范围）与现有 UI 自身给出的承诺（如 RelationDrawer 的「关系 MD（可编辑）」）。
- 证据：`_audit/relation.md`（实测详报）、`_audit/REPORT.md` §2。

### 0. 需求口径：最初文档里的“线（四种，不能混）”

最初决策文档 §8.23 明确写了四种线，**关系是其中一种（正式关系），其余三种是探索来源、虚线关联建议、方向线**：

| 类型 | 含义 | 视觉（§8.23） |
|---|---|---|
| **正式关系** | AI 自动连接 / 手动连线，**不可删除** | 深色实线（管状，较粗） |
| **探索来源关系** | 「本轮从 A 探索到 B」，是**正式关系的一种** | 蓝灰实线 + 起点圆点 |
| **虚线关联建议** | AI 建议、**用户可接受** | 灰色虚线（不等同已建立关系） |
| **方向线** | 下一步探索方向，**无 MD** | 细点线 + 圈问号 |

文档另外两处补充了“体验期望”：

- §3.5 视觉表：正式关系 = **低亮细实线、悬停出标签**、土黄灰、建立时描边生长；建议关联 = 虚线 + 呼吸、金 40%、2.6s 呼吸；下一步方向 = 短虚线箭头 + 问号徽章、更暗、悬停加深。
- §3.4 动效：**虚线建议 → 接受关联（约 600ms）**：虚线呼吸 → 点击 → 虚线 300ms 内转为实线 → **关系名称从 0 到 1 淡入**；关键：让用户「看见关系被确认」，不是「啪」一下变。

由此得到本节判断“体验是否达标”的 4 条标准（只看用户能否做到/看到，不看代码里有没有写）：

1. **可分辨**：四种线在真实地图上是否能一眼区分，不混。
2. **可查看**：正式关系 / 探索来源是否像“已建立的知识连接”一样，能被查看名称、含义、依据。
3. **可确认**：建议是否由用户接受后才变正式，且用户能看见“被确认”的过程。
4. **可修正**：用户发现关系错了/过时/方向不对时，是否有符合产品定义的纠正路径（文档只写了“不可删除”，修正路径需求待补）。

### 1. 发现的体验问题以及和需求的冲突

> 本节只描述**用户实际能感知到的功能现实**，再对照上面的需求/期望。不以“代码里是否存在某字段/某路由”作为问题依据；代码只用于解释现象。

#### 1.1 正式关系：能看到线，但看不到“这条关系是什么”

- **需求/期望**：正式关系是“已建立的知识连接”，应有名称/说明可读；§3.5 写明“悬停出标签”，§3.4 写明接受后“关系名称从 0 到 1 淡入”。
- **现实功能**：地图上能看见一条实线，但**没有名称、悬停没有标签、也点不开**；用户无法在界面上确认这条线叫什么、依据是什么、连接的是哪两个概念（只能靠两端节点的位置猜）。
- **冲突**：**已建立的知识连接不可读**。与“悬停出标签/关系名称”的期望直接冲突；这是“正式关系”这一类线缺失的体验，不是“关系编辑”的附加需求。

#### 1.2 正式关系的说明与修正：文档说“不可删除”，但没给“错误/过时怎么改”

- **需求/期望**：正式关系“不可删除”（这是产品定义，现状与该条一致，不算实现冲突）；但产品整体方向是“知识可编辑”，并且现有 UI 自己提供了「关系 MD（可编辑）」的承诺。
- **现实功能**：正式关系没有可见的说明区，也没有编辑入口——用户想补一句“为什么这条关系成立”、想改关系名（例如把“相关”改成“依赖”），都做不到；能改的只有虚线建议阶段。
- **冲突**：**“不可删除”被现实扩大成了“不可说明、不可修正”**。需求只禁止删除，没有禁止补充/修正，也没有定义“错了怎么办”；这是需求缺口 + 现实功能没有达到“可编辑知识”的期望。

#### 1.3 建议 → 正式：用户没有“确认”的机会，也看不见“被确认”

- **需求/期望**：§8.23 写明建议“用户可接受”、且“不等同已建立关系”；§3.4 要求确认过程可见（呼吸 → 点击 → 转实线 → 名称淡入），让用户“看见关系被确认”。
- **现实功能（两条路径都不符合）**：
  - **语音链路**：用户说完话、停止录音后，系统在提交时会把本轮的虚线建议**批量自动转成正式关系**，用户没有逐条接受/拒绝的动作；也就是说“建议”和“正式”的边界在语音路径上被系统自己抹掉了。
  - **手动接受路径**：用户点开一条虚线建议并接受后，线确实变实，但**原先显示关系名的路牌消失**（正式关系不再有任何标签），并没有出现“名称淡入”；用户看到的是“线变了，然后什么说明都没了”。
- **冲突**：**违反“四种线不能混/建议应由用户接受”的核心语义**，同时违反“让用户看见关系被确认”的动效期望。结果：用户无法区分“我确认过的关系”和“AI 直接替我确认的关系”。

#### 1.4 探索来源关系：需求里是“正式关系的一种、要能看见来路”，现实里不可见

- **需求/期望**：探索来源关系 = 「本轮从 A 探索到 B」，是正式关系的一种；视觉是蓝灰实线 + 起点圆点，用于追溯知识来源。
- **现实功能**：地图上虽然有一条线（视觉上与正式关系同为实线，但无起点圆点、无标签、不可点）；节点抽屉的“关系定位”里也不展示来源关系。用户无法回答“这个知识是从哪句话/哪次探索来的”。
- **冲突**：**需求要求“可区分、可追溯”，现实是“看不见来路”**。这是需求明确写了、但现实功能没有达成的项，不是附加需求。

#### 1.5 方向线：需求要求与建议线明显不同，现实两者视觉接近

- **需求/期望**：方向线 = 下一步探索方向，无 MD；视觉为细点线 + 圈问号（§3.5：短虚线箭头 + 问号徽章，悬停加深）。
- **现实功能**：方向线能被点开（这点符合“可探索”），但视觉上仍是**虚线类**、以路牌文字区分，没有“圈问号/箭头徽章”这类一眼可辨的标识；与建议线同属虚线风格，用户要靠读文字才知道“这是方向，不是建议”。
- **冲突**：**“四种线不能混”中的可分辨性没有达到**；方向和建议在视觉层接近混用。
- 附：方向线“无 MD”这一点现实一致（点开只有方向问题），不算冲突。

#### 1.6 用户编辑与“接受”互相覆盖：先写说明再接受，说明会消失

- **期望**：现有 UI 同时提供「保存」和「接受为正式关系」两个动作，用户自然会先写备注/关系名再接受；用户预期自己写的内容被保留。
- **现实功能**：先保存说明/名称，再点接受，**用户写的内容被 AI 结果静默替换**（关系名、MD 都被改掉），没有任何提示或选择。
- **冲突**：现实功能违背“用户编辑应可见可保留”的基本体验预期。即使产品认为“接受时用 AI 结果覆盖”是合理的，当前 UI 也没有告知用户这条规则——对用户而言就是“我写的东西没了”。

#### 1.7 手动连线：UI 写了方向约定，现实允许连出相反方向

- **期望**：手动连线 UI 提供「归类（具体→上位）」「组成（部分→整体）」「前置（前置→后续）」等带方向的选项，用户按提示选择，期望系统帮自己遵守方向语义。
- **现实功能**：用户选「组成」时，实际生成的关系方向可能与“部分→整体”相反（系统既不校验也不提示）；同一对概念还可以反向各连一条。
- **冲突**：**方向语义只对 AI 抽取生效，对用户手动操作不生效**；用户按 UI 文案操作仍会得到语义错误的关系。

#### 1.8 需求缺口（不是实现缺陷）：四种线里没有“存疑/争议/待确认”这一类

- **现实**：用户对一条 AI 自动建立的关系不认同，能做的只有：接受另一条建议、隐藏整个节点、或者无视；无法单独标记“这条关系存疑/有争议/待核实”。
- **对照**：最初文档的四种线里没有这一类；`02-reasoning.md §6` 曾有 disputed/revised 的设想，但明确标注不是当前实现。因此这**不算**“文档承诺未实现”，而是**产品尚未定义**：如果用户确实需要“关系存疑态”，那是需求要补的一类线/状态，而不是让现有代码背锅。
- 类似地，“正式关系不可删除”是明确设计；真正缺的是 **“不可删除前提下如何纠正错误关系”** 的产品定义（Q3）。

#### 1.9 冲突汇总（按需求层归纳）

| # | 需求/期望（出处） | 现实功能（用户视角） | 冲突性质 |
|---|---|---|---|
| A | 四种线不能混；建议应由用户接受（§8.23） | 语音提交自动把建议批量转正式；手动接受后说明/标签消失 | **核心语义被破坏** |
| B | 正式关系要有名称/说明，悬停出标签（§3.5/§3.4） | 正式关系无名称、无悬停、点不开、不可读 | **可读性缺失** |
| C | 探索来源是正式关系的一种，要可区分、可追溯（§8.23） | 来源线无标签/无起点圆点，节点抽屉也看不到 | **需求写了但没达成** |
| D | 方向线与建议线要一眼可分（§8.23/§3.5） | 两者同为虚线风格，靠文字区分 | **可分辨性不足** |
| E | 用户编辑应保留（现有 UI 双按钮隐含的预期） | 接受会覆盖用户说明/名称 | **编辑被吞** |
| F | 手动连线按 UI 方向约定（UI 文案 + §7 方向约定） | 可连出方向相反的关系 | **辅助语义失效** |
| G | 不可删除（§8.23） vs 知识可编辑 | 不可删除 ≠ 不可修正；错误关系无纠正路径 | **需求缺口**（不是实现 bug） |

### 2. 思考过程以及提出的最终问题可能是什么

#### 2.1 换一个判断轴：用户在“线”上实际要做三件事

1. **看懂**一条已存在的线（它是什么关系、从哪来、依据是什么）；
2. **确认**一条建议（接受/拒绝，并看见确认发生）；
3. **修正**一条线（改名称/说明/方向，或处理错误/过时关系）。

最初文档的四种线，每一类都对应其中一到两件事；**当前现实是“看懂”和“修正”基本不可做，“确认”只有一条不完整的路径**。所以问题不是“某段代码没写”，而是**这三件事没有真正进入用户流程**。

#### 2.2 为什么现实会错位

- 最初文档里“悬停出标签、名称淡入、确认动效、起点圆点”等都属于**样片阶段的交互/视觉设想**；工程实现时只保留了“能画线 + 能点建议路牌”，**展示层（标签/悬停）和确认层（动效/选择）没有一起落地**。
- 语音链路为了“说完就落图”的顺滑，把“建议”在 commit 时直接升级为正式关系，**用系统自动确认替代了用户确认**；它优化了流程速度，却牺牲了“四种线不能混”的产品语义。
- “正式关系不可删除”是明确设计，但产品没有继续定义“错误/过时/有争议怎么处理”，于是现实表现成“只能忍受”，与“知识可编辑”的总方向冲突。

#### 2.3 提炼出的最终问题（等需求侧拍板）

- **Q1（线的语义约束）**：四种线里，哪些是必须遵守的**语义规则**（建议≠正式；来源是正式的一种；方向只是提示），哪些只是**视觉参考**（管状线宽、问号徽章等可降级）？
- **Q2（确认权）**：虚线建议 → 正式关系的“确认权”属于谁？**语音 commit 自动升级算不算用户确认**？如果不算，正确流程是“提交时预览/批量确认/保留建议态”中的哪一种？
- **Q3（修正路径）**：正式关系“不可删除”的前提下，错误/过时关系如何修正——补说明/改名称是必做吗？是否允许“否定/归档”？要不要新增“存疑”这一线型或状态？
- **Q4（可读性下限）**：正式关系/探索来源关系“可查看”的最低要求是什么——悬停标签、点开只读说明、还是可编辑 MD/名称？来源关系是否必须能追溯到来源片段/句子？
- **Q5（编辑仲裁）**：接受建议时，用户已写的名称/说明是保留、提示冲突，还是明确告知会被 AI 覆盖？
- 优先级建议：先 Q1/Q2（决定语义与流程），再 Q4/Q5（决定入口与仲裁），Q3 可与产品下一版规划一起定。
