# 知识世界：实时生成需求基线（只写"必须实现什么"）

日期：2026-11-15
性质：**需求文档**。只描述系统必须表现出的行为、规则与验收标准。
**不包含**实现方式：不规定算法、模型、库、数据库结构、prompt、相似度阈值、episode 时长等；这些属于实现自由，见文末"实现方式不在本文定义"。

状态标记：

- **[已确认]**：来自用户基线 / 已明确确认；
- **[需求]**：由用户提出的问题推导，行为必须满足，细节可再确认；
- **[待确认]**：需要产品拍板的规则。

---

## 1. 目标

用户在桌面浏览器里，通过**流式语音或文字**持续表达自己的理解：

1. 系统实时识别出**值得成为节点**的概念，以及概念之间**有意义的关系**；
2. 节点和关系必须**语义正确、逻辑正确**，能解释、能追溯来源；
3. 随着节点/关系积累，系统在**合适的时候**自动生成**正确且玩家可选择的副本**；
4. 副本要像游戏：出现时机自然、类型正确、玩家有自由度，而不是随机弹窗或凑数。

核心不是"抽到词就建点"，而是四件事同时成立：

```text
实时生成 + 节点/关系语义正确 + 关系识别符合规则 + 副本生成符合规则
```

---

## 2. 对象定义（需求层）

### 2.1 节点

**[已确认]**

- 节点是一个**名词性概念**，不是句子里的任意名词、动词、代词、问句或口头语；
- 节点 MD 记录**由这个概念延伸出的学习、了解、思考**：来源、理解、疑问、类比、资料、关系定位、继续探索；
- 节点有类型、定义（可空但应有来源）、来源片段、别名；
- 节点有题目区，题目通过后改变节点三档形态。

**[需求] 节点准入**

系统必须先判断"什么算节点"，再创建节点。以下不是节点：

- 比喻/类比中的喻体（例："RAG 像灰姑娘"里的灰姑娘）；
- 举例中的例子（除非用户明确要把它作为学习对象）；
- 过程/工作流中的步骤（它们属于流程副本，不是独立节点）；
- 用户玩笑、口头语、代词、修饰语。

节点准入必须回答：

1. 它是这句话的**话题主体**，还是理解主体必需的下位概念？
2. 它**可解释/可出题/以后可能继续学习**吗？
3. 有**关于它的断言或证据**（不只是提到名字）吗？
4. 它属于当前学习范围，或用户**明确主动引入**吗？

只有满足"是学习对象 + 可解释 + 有证据/来源"的候选才成为节点。

**[需求] 过程与步骤**

- 描述一个过程/工作流时，只把**过程本身**作为一个概念节点；
- 过程的有序步骤进入**流程副本**，不单独建节点；
- 只有用户把某一步单独当作学习对象时，它才可能成为节点。

**[待确认]** 节点类型白名单（概念/方法/组件/指标/工具）是否最终固定；是否允许"人物/组织/事件"等其他类型。

### 2.2 关系

**[已确认]**

- 关系不是随便一条线，而是两个概念之间的**归类与定位**；
- 关系有自己的 MD，可编辑；
- 正式关系不可删除；
- 虚线建议 ≠ 已建立关系；
- 方向线没有 MD，只提示下一步。

**[需求] 关系语义**

每条关系必须能回答：

1. 它属于哪类语义（至少区分：归类 / 组成 / 前置 / 对比 / 替代 / 相关）；
2. **方向是什么**（谁指向谁），且方向符合该类语义；
3. **依据是什么**（原文证据或用户说明）；
4. 为什么是这一类，而不是相近的另一类。

"包含"不是独立关系：说"B 包含 A"时，必须落到：

- **A 是 B 的一部分** → 组成关系（部分→整体）；
- **A 是 B 的一种** → 归类关系（具体→上位）。

**[需求] 非知识关系**

比喻、举例、玩笑不进入正式知识关系图；应作为节点 MD 的"类比/例子"内容保存，不参与关系图、不出题、不作为副本依据（具体保存形式待确认）。

**[需求] 关系准入**

只有同时满足以下条件才建立正式关系：

- 两个端点都是节点；
- 有证据/用户说明；
- 语义类型明确；
- 方向明确且符合约定；
- 不是比喻/举例/纯共现。

不满足时：降级为虚线建议、或只记录为笔记、或不建立。

**[需求] 手动关系**

- 用户手动连接两个已有节点时，系统必须给出关系名称/类型/说明（可由 AI 提议，用户确认）；
- 接受 AI 建议后，关系必须从"建议"变为"正式"，并生成可读的关系名/MD。

### 2.3 方向

**[已确认]**

- 每个节点理论上都提供下一步方向；
- 方向线只提示方向，没有 MD；
- 方向线与已建立关系不是同一种状态。

**[需求]**

- 每个节点都有方向数据（0–3 条）；
- 只有边缘节点把方向画成线；非边缘节点的方向在节点 MD 中列出；
- 方向问题必须**具体到本节点**，不能是泛泛的"还能学什么"；
- 方向被探索后消费，不再显示；
- 方向不是关系，不能参与正式关系/副本连通判断。

### 2.4 副本

**[已确认]**

- 副本由系统根据已有知识和节点分析生成，**用户不能自行新建**；
- 必须区分**出现条件**（detected/可见）与**可挑战条件**（playable/可进入）；
- 流程副本：按正确顺序连接步骤，通关后保留、可再次查看，有可编辑 MD；
- 领域副本：同一领域的概念，每天 10 道题（填空/判断/解答混合），持续练习。

**[需求] 流程副本正确性**

- 步骤必须有先后依据；
- 顺序必须**唯一**（多解流程不能作为排序题）；
- 步骤数量、每步来源、粒度一致必须符合规则；
- 成员/步骤必须来自用户的知识图与来源，不能编造。

**[需求] 领域副本正确性**

- 成员必须属于**同一上位/同一领域**，不能只是"都连在同一个节点上"；
- 成员必须有定义/来源；
- 不能与已有领域副本高度重复；
- 题目必须引用成员与依据。

**[需求] 副本出现（游戏感）**

- 不在用户输入/说话过程中打断；
- 只在自然停顿或明确的学习节点（如答完题、打开世界）出现；
- 出现前必须同时满足：知识结构条件、玩家可挑战条件、与当前学习相关；
- 同时出现的"新副本"数量必须受控；
- 玩家可以**稍后再来/忽略**，不应被强制进入；
- 同一副本不重复"出现"；通关后可重玩，但不重复占用"新出现"机会；
- 依据变化（成员隐藏、关系争议、内容修订）时，副本必须标记"依据待更新"，暂停出题，保留历史。

**[需求] 副本自由度**

- 玩家可以在多个候选副本中选择；
- 可以决定何时进入；
- 不同流程/领域可以共存；
- 不能因为"到了阈值"就强制弹出。

## 3. 实时生成需求

**[已确认 / 需求]**

1. 输入支持流式语音与文字；
2. **临时文字只更新 UI，不生成节点**；稳定片段才允许生成；
3. 节点/关系随用户表达**增量出现**，不要求用户先结束整段话；
4. 同一段内容被识别/修订后，旧结果不能重复叠加；新版本应替换旧版本；
5. 不同世界/会话之间不能串数据；
6. 生成失败必须可感知、可重试，不能伪装成功；
7. 一次输入产生多少节点/关系必须有上限，不能刷屏；
8. 系统必须能解释"这个节点/关系是从哪句话来的"。

**[待确认]** 什么算"稳定片段"的判定方式（停顿/标点/时间），以及一次生成的节点/关系上限。

---

## 4. 正确性需求

### 4.1 节点/关系语义正确

- 节点必须是学习对象，不是比喻/例子/步骤/口头语；
- 关系必须有明确谓词和方向；
- 关系证据必须能推出该关系；
- 不能把"相关"当万能关系；
- 不能把比喻/举例当正式关系；
- 同一概念不能因不同说法重复建点；
- 关系方向不能被模型随意反转。

### 4.2 逻辑正确

- 节点不能是孤岛：新节点必须有探索来路（除非是初始节点）；
- 关系不能自环（方向线除外）；
- 同一对概念不能有重复/冲突关系；
- 隐藏/争议必须影响副本依据；
- 方向不能用于正式关系连通。

### 4.3 副本规则正确

- 流程唯一顺序、每步有依据；
- 领域共同上位、成员有定义；
- 出现 ≠ 可挑战；
- 题目必须可追溯；
- 副本依据变化必须失效（stale）。

## 5. 验收场景（可逐条验证）

### V1：比喻不生成节点

输入："RAG 其实感觉和灰姑娘一样，都有一个悲惨的过去。"

必须：

- 只建/更新 RAG 节点；
- 不建"灰姑娘"节点；
- 不建"RAG → 灰姑娘"正式关系或方向；
- "像灰姑娘/悲惨的过去"进入 RAG 节点 MD 的类比/笔记区；
- 不生成关于灰姑娘的题目。

### V2：过程只生成一个过程节点

输入："工作流会依次做输入解析、检索资料、生成草稿、审核发布。"

必须：

- 生成一个过程节点（如"内容生产工作流"）；
- 生成一个流程副本，包含 4 个有序步骤；
- 不为 4 个步骤分别建节点。

### V3："包含"关系可解释

输入："混合检索包含 BM25 和向量召回。"

必须：

- 关系类型正确（组成：部分→整体，或归类：具体→上位）；
- 方向正确；
- 关系卡能说明"为什么是组成/归类，而不是另一类"；
- 不出现方向反转。

### V4：实时增量不重复

连续说多句相关概念：

- 节点增量出现；
- 同义说法合并，不重复建点；
- 不因 ASR 修订重复叠加；
- 每个节点有来源。

### V5：副本出现时机

- 用户正在输入时，不出现新副本；
- 结构条件/玩家条件不满足时，不出现；
- 满足后在自然停顿出现；
- 玩家可稍后再来；
- 同一副本不重复出现。

### V6：副本正确

- 流程副本排序唯一；
- 领域副本成员同一上位、每日 10 题混合、每题有依据；
- detected 不能直接挑战；playable 才能进入；
- 依据变化后 stale。

### V7：关系编辑闭环

- 用户手动连两个节点，系统给出关系名/类型/说明；
- 接受建议后虚线变正式，并有可读关系 MD；
- 正式关系不可删除（按基线）。

## 6. 需求依赖（先满足什么，后满足什么）

```text
R1 输入稳定与实时性
  → R2 节点准入（什么算节点）
    → R3 关系语义与方向
      → R4 增量图一致性（去重/孤儿/来源）
        → R5 方向
          → R6 副本出现条件与时机
            → R7 副本内容与挑战
              → R8 评测与可观测
```

**上游不成立时，下游不能算完成：**

- 节点准入不成立 → 关系再准也是错对象；
- 关系方向不成立 → 副本成员/流程不可信；
- 图一致性不成立 → 副本触发条件失真；
- 副本触发/校验不成立 → 游戏感与正确性都不成立。

## 7. 明确不放在本文的内容（实现方式）

以下都是**实现选择**，不是需求；不得写进验收，也不得把某一种实现当成唯一正确：

- 用什么模型/厂商（DeepSeek、豆包或其他）；
- 流式分段/停顿时长/静音阈值；
- episode 长度、批处理策略；
- prompt 设计、schema 字段实现；
- embedding/相似度阈值；
- 去重/归并算法（规则/向量/LLM 裁决）；
- 数据库表结构、事务方式；
- 方向分数、副本触发公式、冷却时长、上限数值；
- 前端渲染/动效/3D 实现；
- 参考项目（Graphiti、LiveGraph 等）的具体借用方式。

这些由实现阶段决定，可在技术设计文档中讨论；**需求文档只约束行为与验收**。

## 8. 尚待产品确认

1. 比喻/例子是否完全不进图，只进节点 MD？
2. 是否允许"类比/例子"作为非正式注释类型（不参与图/题/副本）？
3. 节点类型白名单是否固定为概念/方法/组件/指标/工具？
4. 关系类型是否固定为归类/组成/前置/对比/替代/相关六类？
5. "自然停顿/合适时机"的判定由产品定义到什么程度？
6. 副本出现后是否允许"稍后再来/不再提示"，以及冷却规则？
7. 一次实时输入最多生成多少节点/关系（产品上限）？
8. 节点是否允许"待确认"层（不直接上地图）？
