# 三个硬问题的解决方案思考：节点准入 / 关系方向 / 谓词校验

日期：2026-11-16
性质：方案思考文档（假设、对比、实验设计），不是已确认实现。
对应报告：`docs/reviews/open-source-solutions-2026-11-15.md`
需求基线：`docs/design/required-implementation.md`

---

## 0. 一句话结论

1. **有流式语音生成节点的开源项目，但它们的"节点"是实体/记忆事实，不是学习对象**；它们靠 LLM schema + 去重 + 重要度/检索价值选实体，不判断"比喻/例子/步骤/教学价值"。
2. **LLM + 搜索有能力判断两个节点的关系、也有能力判断"无关"**；我们做不到，不是因为模型不行，而是因为我们**从来没有这样问过它**：当前是单句开放式抽取，没有成对判定、没有检索、没有"无关"选项、没有证据/方向校验。
3. **"包含"不必作为独立谓词**；它应该被分解为 `partOf`（部分→整体）或 `kindOf`（具体→上位）。LLM 识别不出关系，卡点主要在**语义歧义、缺少关系定义、缺少证据、方向未约束、模型倾向"硬找关系"**，不在"模型不会"。

## 1. 问题一：流式语音节点实时生成，开源怎么决定"新建哪个节点"？

### 1.1 确实有流式/增量图谱项目

| 项目 | 节点是什么 | 怎么决定节点 |
| --- | --- | --- |
| **LiveGraph**（[ACM](https://dl.acm.org/doi/10.1145/3786335.3813169)） | 流式数据中的实体/事实 | 增量抽取 + 更新；公开代码未找到 |
| **Graphiti / Zep**（[GitHub](https://github.com/getzep/graphiti)） | 对话/事件中的实体与事实 | episode 入图、LLM 抽实体、实体去重、时间有效性 |
| **MeetGraph**（[PyPI](https://pypi.org/project/meetgraph/)） | 会议中的实体/关系 | 会议转写 → 图 |
| **cocoindex meeting-notes KG**（[GitHub](https://github.com/cocoindex-io/meeting-notes-knowledge-graph)） | 会议笔记实体 | 持续摄取 + LLM 抽取 + 图更新 |
| **Mem0**（[GitHub](https://github.com/mem0ai/mem0)） | 记忆事实 | 单次抽取（ADD-only）、实体链接 |
| **GraphRAG**（[GitHub](https://github.com/microsoft/graphrag)） | 文档实体/关系 | 批量、schema、类型白名单、多轮补抽 |
| **ACL 2025 概念图**（[论文](https://aclanthology.org/2025.ldk-1.10/)） | 概念 + 关系 | 神经符号管线/LLM，面向文本概念图 |

### 1.2 它们考虑"什么算节点"吗？

**考虑的是"实体抽取"，不是"学习节点准入"。**

- 它们的节点定义通常由 schema/实体类型决定（人、组织、产品、概念、事件）；
- 选节点的依据是：LLM 抽取结果、实体类型、去重/实体链接、重要度/检索价值（如记忆系统里的 importance/salience）；
- 它们**不需要**判断：
  - 这是比喻的喻体还是学习对象？
  - 这是过程步骤还是独立概念？
  - 这个词以后会被出题/复习吗？
  - 这个节点会不会污染教学图？
- 为什么它们可以不做：它们的下游是检索/记忆，噪声的代价是"召回差一点"；我们的下游是**出题、三档、副本**，错节点的代价是**学错、题错、副本错**。

### 1.3 方案思考

**方案 A：候选 → 角色 → 准入（推荐先验证）**

```text
mention/候选
  → 角色判定：topic / subconcept / process / example / metaphor / step / noise
  → 准入：只有 topic、subconcept、process 建节点
  → example/metaphor 写进节点 MD；step 进流程副本；noise 丢弃
```

- 角色判定由 LLM 做，但必须给**定义 + 例子 + 判定问题**；
- 程序校验：名词性、有证据、有定义/可出题、每片段上限；
- 拿不准的进入"候选层"，不直接上地图。

**方案 B：重要度/显著性评分（借记忆系统）**

- 记忆系统会用 importance/salience 决定"记什么、检索什么"；
- 我们可以借来打分：话题显著性、可学习性、复现频率、与当前 focus 的关系、用户明确关注；
- 但**分数只能做辅助**，不能替代角色判定：灰姑娘也可能"显著"，但它不是学习对象。

**方案 C：两层节点**

- "候选节点"（不进地图、不参与关系/副本）与"正式节点"（准入通过）；
- 用户点击/重复提到/明确"记住这个" → 升级；
- 降低误建成本，适合实时流。

**方案 D：流式约束**

- 每个 episode 最多新增 1–3 个正式节点；
- 新节点必须有来源句；
- 同 episode 的步骤/例子/比喻只进笔记；
- 先保证"少而准"，再谈召回。

**需要验证的问题：**

1. LLM 能否稳定区分 topic vs metaphor/example/step？中文效果如何？
2. 角色判定的准确率是否足以支撑自动建点？
3. 用户是否接受"候选层"（不直接上图）？
4. 每片段节点上限对体验的影响？

## 2. 问题二：LLM + 搜索，能不能判断两个节点的关系/无关？

### 2.1 能力边界：能，但有条件

**能做的部分：**

- 给两个节点的名称、定义、MD、已有关系、相关原文，让 LLM 判断：
  - 有关系的谓词是什么；
  - 方向是什么；
  - 证据是哪句；
  - 是否无关/证据不足。
- 搜索可以补：
  - 用户历史转写里同时提到 A/B 的句子；
  - 节点 MD/来源片段；
  - 外部定义（如"BM25 是什么"）作为辅助；
  - 但不能替代"用户自己的理解"这一证据。

**不能保证的部分：**

- LLM 有**虚假关联**倾向：ACL 2024 论文 *Unexpected Phenomenon: LLMs' Spurious Associations in Information Extraction*（[论文](https://aclanthology.org/2024.findings-acl.545/)）发现，即使给定关系标签与原文语义无关，LLM 仍能"识别出"实体对并套上标签；中英文、不同模型规模都出现。
- 所以"能回答"≠"答得对"；必须加**证据、关系定义、无关选项、校验**。

### 2.2 为什么我们的项目做不到？

不是模型不行，是**任务形式不对**：

| 现状 | 缺失 |
| --- | --- |
| 单句开放式抽取：让模型从一句话里抽 entities/relations | 没有"给定 A、B，判断关系/无关"的成对任务 |
| source 缺省为 focus，关系大多是 focus→target | 没有任意两点之间的关系判定 |
| 没有检索：只看当前句 | 没有从用户历史/MD/外部资料找证据 |
| 没有"无关/证据不足"选项 | 模型被迫找关系（虚假关联） |
| 谓词是自由文本/六类但没有判定测试 | 模型不知道 partOf/kindOf 的边界 |
| 方向靠证据顺序启发式 | 没有方向约定 + 校验 |
| 没有置信度/弃权 | 低置信也建正式关系 |
| 没有评测/反馈 | 不知道错在哪、无法迭代 |

### 2.3 方案思考：成对关系判定器

```text
输入：A（名称/定义/MD/来源）、B（同）、候选证据（用户转述/历史/MD/外部）
任务：输出
  - relation: kindOf / partOf / prerequisite / contrast / alternative / related / unrelated
  - direction: A→B / B→A / 无方向
  - evidence: 支持该判断的原文句
  - confidence + reason
  - 如果证据不足：unrelated 或 unknown（不建正式关系）
```

关键设计：

1. **把"无关"作为一等输出**，并明确"没有证据默认无关/未知"；
2. **先检索证据，再判定**：优先用户自己的话，其次节点 MD，最后外部；
3. **关系测试题**（见 §3）：让模型回答"A 是 B 的一部分吗/A 是 B 的一种吗/A 必须在 B 之前吗"；
4. **方向约定**：输出后用程序校验方向；证据顺序冲突时要求重判；
5. **多假设 + 置信度**：低置信进建议/待确认，不直接实线；
6. **label validation**：借 ACL 2024 的 forward label extension / backward label validation 思路，验证"这个标签是否真的适合这对实体"；
7. **人工确认**：争议/低置信让用户点一下，形成反馈。

### 2.4 搜索在这里的角色

- **用户语料检索**（首选）：从历史转写、节点 MD、来源片段里找同时涉及 A/B 的句子；
- **外部搜索**（辅助）：查定义、类别、前后关系；必须标注来源、可关闭、防止把外部观点当用户知识；
- **不要用搜索替代证据**：搜索能告诉你"BM25 是检索算法"，但不能证明"用户把 BM25 归到了检索技术"。

**结论：LLM + 搜索能判断关系/无关；我们做不到是因为没有把任务设计成"成对判定 + 证据 + 无关 + 校验"，而不是模型能力不足。**

## 3. 问题三：谓词校验——"包含"有必要吗？LLM 为什么识别不出来？

### 3.1 "包含"有必要作为关系出现吗？

**作为自然语言词：有必要理解；作为存储谓词：不必要。**

"包含"至少有三种含义：

1. **部分-整体**：混合检索包含 BM25 → `partOf`（BM25 → 混合检索）；
2. **类别-实例**：RAG 包含"检索增强生成"这一种方法 → `kindOf`（具体 → 上位）；
3. **文本/集合包含**：这句话包含"RAG"这个词 → 不是知识关系。

如果保留一个独立的 `contains` 谓词，会把三种语义混在一起，方向也无法定义。**正确做法：把"包含"当作语言线索，分解成 `partOf` 或 `kindOf`；不能分解就不建关系。**

### 3.2 LLM 为什么识别不出来？卡点在哪？

| 卡点 | 说明 |
| --- | --- |
| **语义歧义** | "包含/属于/是"本身多义；没有关系定义时模型只能猜 |
| **没有关系测试** | 没让模型回答"是部分还是种类"，直接让它给标签 |
| **缺少上下文** | 只看一句话，没有节点定义/MD/历史证据 |
| **方向未约束** | 模型可能给对谓词但方向反（"召回后精排"→Rerank→召回） |
| **虚假关联** | ACL 2024：给定标签，LLM 会把无关实体对也套上关系 |
| **没有"无关"** | 模型倾向输出一个关系，而不是"证据不足" |
| **标签体系不互斥** | partOf/kindOf/related 边界不清，模型自由发挥 |
| **没有验证** | 没有程序检查方向/环/证据/重复 |
| **任务本身难** | 概念图抽取 SOTA F1 也只有 25–28（ACL 2025），说明这是研究级难题 |

**卡点总结：不是"模型不认识包含"，而是我们没有给它可判定的问题、证据和约束。**

### 3.3 方案思考：把谓词变成"可回答的问题"

对每一对候选节点，按顺序问：

1. **A 是 B 的一部分吗？**（partOf：部分→整体）
2. **A 是 B 的一种吗？**（kindOf：具体→上位）
3. **A 必须在 B 之前学习吗？**（prerequisite：前置→后续）
4. **A 与 B 是替代关系吗？**（alternative：旧→新）
5. **A 与 B 是对比关系吗？**（contrast：无方向）
6. **有明确证据支持 A 与 B 相关吗？**（related：无方向，仅证据强时）
7. **以上都没有 → unrelated / unknown，不建正式关系。**

配套：

- 每个"是"必须给证据句；
- 方向由问题本身决定（部分→整体、具体→上位、前置→后续）；
- 程序校验：环、方向冲突、同对多谓词、重复；
- 低置信 → 虚线/待确认；
- 评测集覆盖"包含/属于/否定/比喻/多谓词/证据不足"。

**"包含"在 UI 上可以作为解释文案**（"BM25 是混合检索的一部分"），但**存储层只保留 partOf/kindOf**。

## 4. 三者的关系

```text
节点准入（上游）
  → 决定"谁有资格进图"
  → 关系成对判定（中游）
    → 决定"两点是什么关系、方向、证据、是否无关"
    → 谓词校验（中游）
      → 决定"这条关系能不能作为正式知识"
      → 副本/题目/方向（下游）
```

上游错，下游全错：

- 灰姑娘进了图 → 关系判定再准也是错对象；
- 关系方向错 → 流程副本排序答案错；
- 谓词错 → 领域副本把组件当领域、题目依据错。

## 5. 建议的实验（先验证，不急着改代码）

### 实验 1：节点角色判定

- 20–30 句真实语音转写（含比喻/例子/步骤/口头语）；
- 人工标注角色；
- 对比：直接抽取 vs 角色判定 + 准入；
- 指标：误建率（尤其 metaphor/example/step）、节点召回、每句节点数。

### 实验 2：成对关系判定

- 20–30 对节点（含无关对、方向对、包含对）；
- 给 LLM 名称+定义+证据，要求输出关系/方向/无关；
- 对比：单句抽取 vs 成对判定 vs 成对判定+检索；
- 指标：谓词准确率、方向合法率、无关判断准确率、证据覆盖率。

### 实验 3：谓词测试题

- 同一批对，用"部分/种类/前置/替代/对比/无关"问题链；
- 对比直接给标签 vs 问题链；
- 指标：partOf/kindOf 混淆率、方向错误率。

### 实验 4：外部搜索增益

- 对"BM25/RAG/微调"等术语对，比较无搜索 vs 用户语料检索 vs 外部搜索；
- 指标：准确率增益、延迟、错误来源（外部噪声）。

## 6. 结论

1. **开源有流式节点生成，但没有"学习节点准入"**；它们的节点是实体/记忆，不是教学资产，所以可以不处理比喻/步骤/教学价值。
2. **LLM + 搜索能判断关系与无关**；我们做不到是任务设计问题（单句抽取 vs 成对判定、无检索、无关缺失、无校验）。
3. **"包含"不必作为独立谓词**；它是语言线索，应分解为 partOf/kindOf。LLM 的卡点是歧义、缺定义、缺证据、方向未约束、虚假关联、无 abstain、无验证。

**下一步建议：先做实验 1 和 2（各 20–30 条），用数据决定"角色判定 + 成对判定"是否足够，而不是先改架构。**

## 8. 补充：开源节点 vs 我们的节点，区别到底在哪

| 维度 | 开源实体/记忆节点 | 我们的学习节点 |
| --- | --- | --- |
| 语义角色 | 实体（人/组织/产品/概念）或记忆事实 | **学习对象**：概念/方法/组件/指标/工具/过程 |
| 粒度 | mention/实体，抽到就建 | 必须先过角色与准入：topic/subconcept/process 才是节点；example/metaphor/step/noise 不是 |
| 内容 | 属性、事实、描述 | **节点 MD**：用户的理解、疑问、类比、资料、关系定位、继续探索 |
| 状态 | 时间有效性、检索分数 | **tier/掌握度、题目、方向、frontier、隐藏/争议** |
| 下游 | 检索、问答、记忆召回 | **出题、三档、副本、地图生长** |
| 所有权 | 系统/Agent 的记忆 | **用户的学习资产**（可编辑、可纠正、长期保存） |
| 错误成本 | 检索噪声，少召回一点 | **学错、题错、副本错、地图污染**，纠错成本高 |

一句话：**开源的节点是"指针/事实锚点"，我们的节点是"一张带学习闭环的卡片"**。所以它们可以容忍大量实体，我们不能。

### 8.1 我们额外需要的，不只是关系

1. **节点角色与准入**（什么算学习对象）；
2. **粒度控制**（过程 vs 步骤，话题 vs 例子/比喻）；
3. **证据与来源**（这句话从哪来、能不能出题）；
4. **关系语义与方向**（谓词、方向、无关）；
5. **学习状态**（题目、tier、方向、frontier）；
6. **纠错与所有权**（改名/合并/隐藏/争议/撤销）；
7. **副本成员与游戏身份**（节点是副本/建筑/方向的一部分）；
8. **评测**（节点/关系/副本的质量口径）。

关系是其中**最核心的语义层**，但不是唯一层。

## 9. 如果"同步判断关系、无关就不连线"，能解决吗？

### 9.1 能解决的部分

- **假关系/虚假关联**：无关的两点不建边，图会干净很多；
- **比喻/例子被当知识关系**：如果判定为 analogy/example，不建正式边；
- **方向/谓词错误**：成对判定可以要求方向与证据，减少"related 万能化"；
- **副本依据**：流程/领域不会因为错误边而误生成。

### 9.2 不能解决的部分

如果只是"不连线、但节点已经建了"：

- 灰姑娘仍然是地图上的节点，仍然可以点开、写 MD、出题、占节点数；
- 它可能通过"探索来源线"（focus→新节点）继续挂在图上，**没有真正消失**；
- 它仍可能进入领域簇/副本成员/统计；
- 过程句仍可能生成 4 个"环节"节点，只是彼此不连线；
- 节点没有定义/不可出题的问题仍在；
- 用户仍无法纠正误建节点。

**所以"不连线"只解决了边，不解决节点。**

### 9.3 关键升级：关系优先的节点准入（relation-gated admission）

把规则从"建节点 → 判断关系 → 无关就不连线"改成：

```text
候选
  → 先判断它在当前图谱里有没有"有意义的关系"
    → 有：建节点 + 建关系（角色允许时）
    → 没有：
       - 如果是用户明确要学的新主题 → 建节点（标记 user-introduced），但暂不建知识关系
       - 如果是比喻/例子 → 写进节点 MD，不建节点
       - 如果是步骤 → 进流程副本，不建节点
       - 如果是无关噪声 → 丢弃或候选层
```

也就是说：

- **节点准入 = 角色合格 + 至少一条有意义的关系（或用户明确引入/初始节点）**；
- **关系判定 = 谓词 + 方向 + 证据 + 无关/未知**；
- "无关"不只是"不连线"，而是**"不建节点"**（除非用户明确引入）。

这样，灰姑娘用例会变成：

- 角色 = metaphor → 不建节点（写进 RAG MD）；
- 即使角色误判为 concept，成对判定 RAG↔灰姑娘 = analogy/unrelated → 不建正式关系 → 不建节点；
- 双保险，而不是只靠一个分类器。

### 9.4 需要小心的边界

1. **新主题没有关系**：用户说"我想学 BM25"，此时 BM25 与现有图可能还没有语义关系。规则必须允许"用户明确引入"的节点（带 user-introduced 来源），否则会阻止正常学习。
2. **来源线 ≠ 知识关系**：不能因为"探索来源线"存在，就认为节点有关系；来源线只表示"从哪来"。
3. **关系判定的假阴性**：把本来有关系判成无关，会丢节点；需要"候选层/待确认"兜底。
4. **LLM 虚假关联**：成对判定也会硬找关系，必须要求证据 + 允许 unrelated + 校验。
5. **角色与关系要联合判断**：同一句"工作流依次做 A/B/C"里，工作流是 process，A/B/C 是 step；不能先全建节点再判关系。

### 9.5 结论

- **只做"关系判断 + 无关不连线"不够**；
- **但把关系判断前置为节点准入门槛，可以同时解决节点污染和关系噪声**；
- 这可能是比"单独做复杂节点分类器"更简洁的架构：**角色判定 + 成对关系判定 + 关系优先准入**。

## 10. 建议的实验（验证"关系优先准入"是否成立）

同一批 20–30 句真实转写（含灰姑娘/工作流/BM25/无关词），三种策略对比：

| 策略 | 做法 | 预期 |
| --- | --- | --- |
| A 现状 | 开放式抽取，建节点，再判关系 | 节点多、假关系多 |
| B 角色准入 | 先判角色，再建节点 | 节点减少，但可能漏新主题 |
| C 关系优先 | 角色 + 成对关系判定；无关不建节点（用户明确引入除外） | 节点最准、关系最干净 |

指标：

- 节点 precision/recall（重点：metaphor/example/step 误建率）；
- 关系 precision/recall（重点：无关对、方向反、谓词错）；
- 孤儿率、副本误生成率；
- 新主题召回（BM25 这类"用户明确引入"是否被误杀）；
- 用户纠错次数。

如果 C 在"灰姑娘/工作流"上明显优于 A/B，就说明**关系优先准入**是正确方向。

## 11. 补充：你提的"锚点 → 候选 → 成对判定 → 有 关系才生成"可行吗？时间够吗？

### 11.1 你的方案拆开是什么

```text
流式输入（按学习顺序）
  → 必须提到地图里的一个已有节点（锚点）
  → 抽取候选（开源/LLM）
  → 判断"锚点 ↔ 候选"有没有关系
  → 有关系才生成节点+关系；没关 系就不生成
```

这本质就是我前面说的 **关系优先准入（relation-gated admission）**，方向是对的。

### 11.2 它能解决什么

- 每个新节点都有锚点、有关系，不会出现"凭空建点"；
- 关系是经过"锚点-候选"成对判定后才建的，比单句开放式抽取更干净；
- 无关候选不生成，减少灰姑娘类污染；
- 用户按学习顺序说，锚点通常明确。

### 11.3 它不能自动保证什么

1. **"有关系"不等于"关系正确"**：LLM 仍可能虚假关联（ACL 2024），需要证据 + 谓词/方向校验 + 置信度；
2. **"没关 系"不等于"不该建节点"**：用户可能明确要学一个新主题（BM25），此时没有关系也应该允许（标记 user-introduced）；
3. **步骤/比喻仍要角色判定**：工作流的步骤即使与工作流有 partOf 关系，也不应该建节点；
4. **多锚点/多候选**：一句话提到两个已有节点、三个候选，不能只判一对；
5. **锚点缺失**：用户没说已有节点时，必须有兜底（当前 focus / 询问 / 候选层），否则会漏掉正常输入。

### 11.4 延迟实测（当前本地环境）

当前 `/extract` 一次请求包含两次 DeepSeek 调用（抽取 + 方向），实测：

| 次数 | 耗时 | 结果 |
| --- | --- | --- |
| 第 1 次 | **4,964 ms** | 5 节点 / 9 边 / 8 方向 |
| 第 2 次 | **3,852 ms** | 0 新节点 / 3 边 / 8 方向 |

> 说明：本地开发环境、DeepSeek 云端、包含两次 LLM 调用与落图；不是生产 P95。

### 11.5 如果按"每对候选都调一次 LLM"算

- 一句话有 3 个候选、2 个锚点 = 6 对；
- 每对关系判定 1.5–2.5s；
- 串行 = **9–15 秒**，不可接受。

### 11.6 可行的延迟预算（目标：说完一句 2–4 秒内落图）

| 步骤 | 方案 | 预估 |
| --- | --- | --- |
| ASR final | 豆包 | 0.3–0.8s |
| 锚点识别 | 别名表/embedding 匹配已有节点 | <100ms |
| 候选抽取 | 本地小模型（GLiNER）或一次 LLM | 0.2–1.5s |
| 候选剪枝 | 共现/embedding/词面，取 top 1–3 | <100ms |
| **成对关系判定** | **一次 LLM 调用批量判所有候选×锚点** | **1.5–2.5s** |
| 程序校验 | 谓词/方向/环/重复 | <50ms |
| **合计（串行）** | — | **约 2–4.5s** |

关键：**一次批量判定，而不是每对一次**。

### 11.7 要做到"过得去"，必须做这几件事

1. **批量成对判定**：把"锚点列表 + 候选列表 + 证据"一次给模型，输出所有关系/无关；
2. **候选剪枝**：只判 top 1–3 个候选，不判全部；
3. **异步流水线**：ASR final 后先显示"关联中"，关系判定完成再落图；用户可继续说下一句，上一句在后台处理；
4. **本地小模型做候选/锚点匹配**：GLiNER/别名/embedding，避免每步都走云端 LLM；
5. **方向生成延后**：先落节点/关系，方向可以第二批生成，不阻塞主链路；
6. **缓存**：节点定义/已有关系/别名表常驻内存；
7. **超时/降级**：关系判定超时先落"候选/待确认"，不阻塞用户。

### 11.8 结论

- **时间上可以过得去，但前提是"批量判定 + 剪枝 + 异步"**；
- 如果按"每个候选每对锚点串行调 LLM"，一定不可接受；
- 当前单次抽取 4–5s 已经接近上限，再叠加成对判定会超时；必须把"抽取 + 关系判定"合并或并行，并减少一次调用（例如方向生成延后/合并）。

### 11.9 建议的验证

先不写完整实现，做一个**离线延迟模拟**：

- 取 20 句真实材料，mock 候选和锚点；
- 测三种：
  A. 每对一次 LLM；
  B. 一次批量 LLM；
  C. 本地小模型候选 + 一次批量 LLM；
- 记录 P50/P95、准确率；
- 如果 B/C 的 P95 ≤ 4s 且关系准确率可接受，再进入实现。
