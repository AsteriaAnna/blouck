## 1. 节点准入：什么值得成为节点

### 问题

LLM 倾向于把一段话里的**所有名词**都识别成实体；但地图节点是学习对象，不是 mention。

典型错误：

- "RAG 和知识库的关系像白雪公主里后妈派猎人追杀公主一样" → 抽出白雪公主、猎人、公主、后妈；
- 工作流步骤被建成节点；
- 口头语、代词、玩笑被建成节点。

### 尝试

1. **纯 LLM 抽取**：能抽到，但无法判断"值不值得建"；
2. **角色过滤**（topic/subconcept/process/example/metaphor/step/noise）：
   - 能排除喻体/例子/步骤，但角色分类本身不稳；
   - 雪白句测试里，LLM 一度把 RAG 判成 metaphor/noise，需要 prompt 规则纠正；
3. **锚点优先**：先有已有节点作锚点，候选与锚点做关系快判；无关不建；
4. **关系优先准入**：没有有意义的关系就不建节点（用户明确引入的新主题例外）；
5. **MD-first 收敛**：节点 = 学习锚点 + MD；`type` 可选/可后补；领域细节写 MD，不新增节点/边。

### 当前处理

- 节点准入看四问：是话题主体/必需下位概念吗？可解释/可出题吗？有断言或证据吗？属于当前范围或用户明确引入吗？
- 比喻/例子/步骤不进节点；步骤进流程副本；
- 不强制类型；
- 关系判定允许 `unrelated`；没有证据不建正式关系；
- 主题节点可以"先建、关系待确认"。

### 未决

- 角色分类的准确率还不够，尤其是中文隐喻/否定/指代；
- "话题节点无关系先建"与"没关系不建节点"的边界；
- 没有稳定的节点准入评测集。

## 2. 关系方向：同一关系不能画反

### 问题

同一对概念，模型经常把方向画反：

- `partOf` 整体→部分 / 部分→整体混用；
- `prerequisite` 前置→后续画反；
- "A 包含 B" 直接存成 `contains`，不知道是 `partOf` 还是 `kindOf`。

### 尝试

- 固定方向表；
- 用证据句的实体顺序归一；
- 程序校验 + 置信度；
- 把"包含"映射到 `partOf`（部分→整体）或 `kindOf`（具体→上位），不新增谓词。

### 当前方向约定

| 谓词 | 方向 |
| --- | --- |
| `kindOf` | 具体 → 上位 |
| `partOf` | 部分 → 整体 |
| `prerequisite` | 前置 → 后续 |
| `contrast` | 无方向 |
| `related` | 无方向 |
| `alternative` | 旧 → 新 |

### 未决

- `partOf` 的传递性例外（部分的部分）；
- 同一对节点是否允许多谓词（建议最多 2，层级与 `related` 不相交）；
- 关系错误后的更正流程（正式关系不可删除）。

## 3. 谓词校验：`partOf` 万能化

### 问题

测试中"混合检索把 BM25 和向量召回合并"被全部判成 `partOf`：

- 混合检索不是 RAG 的一部分；
- BM25/向量召回是混合检索的组件，`partOf` 可以；
- Rerank 是阶段，更适合 `related(阶段)` 或 `prerequisite`。

模型倾向用一个谓词覆盖所有"有关联"的情况。

### 尝试

- prompt 里加谓词消歧规则：
  - "是一种" → `kindOf`；
  - "由…组成/包含组件" → `partOf`；
  - "使用/从…获取/来源" → `related(使用/来源)`，不要 `prerequisite`；
  - "组合了…" → `related(组合)`，不要 `partOf`；
- 证据/置信度门槛；
- 自由标签承载领域细节（衡量/组合/使用/阶段），不强行扩谓词。

### 当前处理

- 首版只保留 5 个核心谓词 + 可选 `alternative`；
- 领域语义先用 `related + label` 或节点 MD；
- 只有反复出现且需要程序推理时，才升级为一等谓词。

### 未决

- 包含句仍会把"混合检索"判成 `partOf`；
- 需要一套"部分/种类/前置/对比/无关"问题链，而不是一次自由 prompt；
- 谓词准确率基线 87%，但样本小。

## 4. 流式与延迟：怎样像"言出法随"

### 问题

- 当前 `/extract` 一次 3.9–5.0s（两次 LLM 调用，本地实测）；
- 逐对判关系不可接受（3 候选 × 2 锚点 × 1.5–2.5s ≈ 9–15s）；
- 句末才生成节点，用户感觉"说完才动"。

### 尝试

1. **锚点优先（A 方案）**：
   - 锚点 → 候选 → 快筛 → provisional → 慢判 → commit/修复；
   - 一次批量关系判定，目标 2–4.5s；
   - A1 严格（无关系不建）/ A2 话题优先（topic 先建、关系待确认）。
2. **角色优先（B 方案）**：
   - 先角色分类，再关系判定；
   - 没有直接证据，作为并列假设，未采用。
3. **MD-first**：
   - 不搞 15 谓词/6 类型重本体；领域细节进 MD/自由标签。
4. **流式 ghost**：
   - partial 匹配已有节点 → 高亮；
   - 每增长 6 字符 detect 一次 → 候选 ghost；
   - final 全量 detect → extract；
   - 新节点从 ghost 位置起飞到最终位置。

### 当前处理

```text
partial → 多步 detect → ghost
final → 全量 detect → 现有 /extract
extract 返回 → 新节点按名字匹配 ghost → 起飞动画
```

测试结果：

| 场景 | 结果 |
| --- | --- |
| 雪白句 A1 | 不建 RAG；白雪公主等排除；总 2.4s（预置候选） |
| 雪白句 A2 | 只建 RAG；无类比正式关系 |
| 检索句 | RAG + `related(使用/检索)` |
| 包含句 | 5 节点；混合检索仍 `partOf`（错） |
| 端到端（含抽取） | 2.8–4.6s；流式 final 补检后约 6–9s |

### 未决

- ghost 只是前端预览，不是 provisional 实体；
- detect 与 extract 是两条链路，结果可能不一致；
- final 补检 + extract 串行，延迟损害"言出法随"；
- 没有确认/拒绝/修复/重新映射；
- 没有真正逐词/逐实体提交。

## 6. 新问题（2026-11-16）：言出法随未达成 + 多跳节点全挂到同一节点

### 6.1 用户观察到的现象

1. **生成速度不够**：说话过程中地图反应不够快，ghost 不够连续；
2. **ghost 和后面的实体没接上**：候选消失/节点另起，缺少同一身份；
3. **空白图谱里一句话生成 3 个节点**：3 个都围绕当前唯一的核心节点；
4. **多跳关系错**：用户说 1 → 2 → 3，系统只判断 2、3 和 1 的关系；2 和 3 都挂到 1；关系不明确时 2/3 可能不生成。

### 6.2 第一性原理拆分

**目标不是"动画更快"，而是"每个稳定语义单元出现时，地图状态立刻有对应变化"。**

要拆成四个独立问题：

| 问题 | 本质 |
| --- | --- |
| 什么时候反应 | 稳定片段/实体 mention，不是整句 |
| 反应什么 | 当前话语的焦点、父节点、候选关系 |
| 什么是真的 | provisional 状态，不是 UI 影子 |
| 多快 | 本地检测 + 异步验证，不是把 LLM 调快 |

节点归属不是"全局初始节点"，而是**话语中的当前焦点/父链**；关系不是"新节点 vs 锚点"，而是"新节点 vs 已有图（含同句新节点）"。

### 6.3 为什么现在会这样（代码核对）

已核对 `server/src/index.ts` 的 `/extract` 与 `providers/deepseek.ts`：

1. **所有新节点都围绕 focus 摆放**：`placeAround(placed, {focus.x, focus.y})`；
2. **所有来源线都从 focus 出发**：`addEdge(focus.id, n.id, "source", ...)`，并有"孤岛禁令"兜底；
3. **关系 source 缺省为 focus**：`const source = (rel.source && findExisting(rel.source)) || focus`；
4. **prompt 只给"当前节点"**，没有"这句话里谁接谁/父节点链"的字段；
5. **前端 `focusId` 不随新节点更新**：抽取完成后只更新 nodes/edges，focus 仍是初始节点；
6. **detect 与 extract 是两套独立结果**：ghost 只按名字匹配，没有 ID/父节点/关系，所以接不上；
7. **final 全量 detect + extract 串行**：延迟叠加。

所以现象不是"模型不会"，而是**数据模型里没有"这句话的父节点/话语焦点"这个概念**，程序只能用全局 focus 兜底。

### 6.4 为什么 ghost 不能解决这个问题

Ghost 目前是：

```text
检测候选 → 前端 ghost → final 重新 extract → 按名字匹配 ghost → 动画
```

它只解决"视觉上先出现"，没有解决：

- ghost 的 ID 与最终节点 ID 不同；
- ghost 没有父节点/关系；
- final 重新抽取会改名字、改数量、改归属；
- 没有 provisional 状态，刷新即丢。

**Ghost 是 UI 层补丁；多跳归属是数据模型问题，不能靠动画修。**

### 6.5 解决方向（先不写实现）

#### 最小修复（不改架构）

- 维护"当前话语焦点"（focus cursor），每引入一个新实体就推进；
- 每个候选实体必须带 `parent`（父节点名/ID）+ 证据；
- 关系候选不只对 focus，而是对"同句新节点 + 已有节点"；
- 来源线按 parent 建，不再统一挂 focus；
- 关系不明确时先 `suggest`，不要静默丢弃。

#### 目标架构（对应"言出法随"）

```text
稳定 mention / 片段
  → provisional 实体（ID + 父节点 + 候选关系）
  → 地图立即渲染 provisional
  → 异步验证/合并
  → commit 为正式节点（同一 ID）
  → 失败/无关 → tombstone / 撤回
```

需要：focus stack、provisional 表、revision、幂等、reconciliation。

#### 速度

- 本地 mention/alias/embedding 匹配：<100ms；
- LLM 只做异步实体/关系验证，不阻塞首次渲染；
- 批量关系判定，不逐对调用；
- final 不再"全量重抽"，只确认 provisional。

### 6.6 需要产品拍板

1. 一句话是否允许多个新节点/多跳（1→2→3）？
2. 父节点规则：最近引入的实体 / 当前焦点 / 显式关系？
3. 关系不明确时：挂当前焦点（suggest） / 不建 / 等下一句？
4. "言出法随"的目标延迟：mention <100ms、provisional <1s、commit 2–4s？
5. 是否接受"先 provisional、后修正"的可见状态？
