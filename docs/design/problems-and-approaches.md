## 1. 节点准入：什么值得成为节点

### 问题

LLM 倾向于把一段话里的**所有名词**都识别成实体；但地图节点是学习对象，不是 mention。

典型错误：

- "RAG 和知识库的关系像白雪公主里后妈派猎人追杀公主一样" → 抽出白雪公主、猎人、公主、后妈；
- 工作流步骤被建成节点；
- 口头语、代词、玩笑被建成节点。

### 尝试

1. **纯 LLM 抽取**：能抽到，但无法判断"值不值得建"；
2. **角色过滤**（topic/subconcept/process/example/metaphor/step/noise）：
   - 能排除喻体/例子/步骤，但角色分类本身不稳；
   - 雪白句测试里，LLM 一度把 RAG 判成 metaphor/noise，需要 prompt 规则纠正；
3. **锚点优先**：先有已有节点作锚点，候选与锚点做关系快判；无关不建；
4. **关系优先准入**：没有有意义的关系就不建节点（用户明确引入的新主题例外）；
5. **MD-first 收敛**：节点 = 学习锚点 + MD；`type` 可选/可后补；领域细节写 MD，不新增节点/边。

### 当前处理

- 节点准入看四问：是话题主体/必需下位概念吗？可解释/可出题吗？有断言或证据吗？属于当前范围或用户明确引入吗？
- 比喻/例子/步骤不进节点；步骤进流程副本；
- 不强制类型；
- 关系判定允许 `unrelated`；没有证据不建正式关系；
- 主题节点可以"先建、关系待确认"。

### 未决

- 角色分类的准确率还不够，尤其是中文隐喻/否定/指代；
- "话题节点无关系先建"与"没关系不建节点"的边界；
- 没有稳定的节点准入评测集。

## 2. 关系方向：同一关系不能画反

### 问题

同一对概念，模型经常把方向画反：

- `partOf` 整体→部分 / 部分→整体混用；
- `prerequisite` 前置→后续画反；
- "A 包含 B" 直接存成 `contains`，不知道是 `partOf` 还是 `kindOf`。

### 尝试

- 固定方向表；
- 用证据句的实体顺序归一；
- 程序校验 + 置信度；
- 把"包含"映射到 `partOf`（部分→整体）或 `kindOf`（具体→上位），不新增谓词。

### 当前方向约定

| 谓词 | 方向 |
| --- | --- |
| `kindOf` | 具体 → 上位 |
| `partOf` | 部分 → 整体 |
| `prerequisite` | 前置 → 后续 |
| `contrast` | 无方向 |
| `related` | 无方向 |
| `alternative` | 旧 → 新 |

### 未决

- `partOf` 的传递性例外（部分的部分）；
- 同一对节点是否允许多谓词（建议最多 2，层级与 `related` 不相交）；
- 关系错误后的更正流程（正式关系不可删除）。

## 3. 谓词校验：`partOf` 万能化

### 问题

测试中"混合检索把 BM25 和向量召回合并"被全部判成 `partOf`：

- 混合检索不是 RAG 的一部分；
- BM25/向量召回是混合检索的组件，`partOf` 可以；
- Rerank 是阶段，更适合 `related(阶段)` 或 `prerequisite`。

模型倾向用一个谓词覆盖所有"有关联"的情况。

### 尝试

- prompt 里加谓词消歧规则：
  - "是一种" → `kindOf`；
  - "由…组成/包含组件" → `partOf`；
  - "使用/从…获取/来源" → `related(使用/来源)`，不要 `prerequisite`；
  - "组合了…" → `related(组合)`，不要 `partOf`；
- 证据/置信度门槛；
- 自由标签承载领域细节（衡量/组合/使用/阶段），不强行扩谓词。

### 当前处理

- 首版只保留 5 个核心谓词 + 可选 `alternative`；
- 领域语义先用 `related + label` 或节点 MD；
- 只有反复出现且需要程序推理时，才升级为一等谓词。

### 未决

- 包含句仍会把"混合检索"判成 `partOf`；
- 需要一套"部分/种类/前置/对比/无关"问题链，而不是一次自由 prompt；
- 谓词准确率基线 87%，但样本小。

## 4. 流式与延迟：怎样像"言出法随"

### 问题

- 当前 `/extract` 一次 3.9–5.0s（两次 LLM 调用，本地实测）；
- 逐对判关系不可接受（3 候选 × 2 锚点 × 1.5–2.5s ≈ 9–15s）；
- 句末才生成节点，用户感觉"说完才动"。

### 尝试

1. **锚点优先（A 方案）**：
   - 锚点 → 候选 → 快筛 → provisional → 慢判 → commit/修复；
   - 一次批量关系判定，目标 2–4.5s；
   - A1 严格（无关系不建）/ A2 话题优先（topic 先建、关系待确认）。
2. **角色优先（B 方案）**：
   - 先角色分类，再关系判定；
   - 没有直接证据，作为并列假设，未采用。
3. **MD-first**：
   - 不搞 15 谓词/6 类型重本体；领域细节进 MD/自由标签。
4. **流式 ghost**：
   - partial 匹配已有节点 → 高亮；
   - 每增长 6 字符 detect 一次 → 候选 ghost；
   - final 全量 detect → extract；
   - 新节点从 ghost 位置起飞到最终位置。

### 当前处理

```text
partial → 多步 detect → ghost
final → 全量 detect → 现有 /extract
extract 返回 → 新节点按名字匹配 ghost → 起飞动画
```

测试结果：

| 场景 | 结果 |
| --- | --- |
| 雪白句 A1 | 不建 RAG；白雪公主等排除；总 2.4s（预置候选） |
| 雪白句 A2 | 只建 RAG；无类比正式关系 |
| 检索句 | RAG + `related(使用/检索)` |
| 包含句 | 5 节点；混合检索仍 `partOf`（错） |
| 端到端（含抽取） | 2.8–4.6s；流式 final 补检后约 6–9s |

### 未决

- ghost 只是前端预览，不是 provisional 实体；
- detect 与 extract 是两条链路，结果可能不一致；
- final 补检 + extract 串行，延迟损害"言出法随"；
- 没有确认/拒绝/修复/重新映射；
- 没有真正逐词/逐实体提交。

## 6. 核心问题：不是单 Focus，而是缺少话语状态模型（2026-11-16）

### 6.1 最初看到的现象

1. 说话时地图反应不够快，ghost 不够连续；
2. ghost 和最终实体接不上，候选消失后节点像另起；
3. 空白图谱里一句话生成 3 个节点，3 个都围绕同一个核心节点；
4. 用户说 1 → 2 → 3，系统只判断 2、3 和 1 的关系，2 和 3 都挂到 1。

这些是表层现象。继续往下挖，真正的问题不是"focus 不准"，而是**系统没有多焦点/父链这个数据模型**。

### 6.2 真正的问题：多焦点与父链

真实对话会不断切换焦点。以 RAG 为例：

```text
RAG
├─ 检索
│  ├─ 语义检索
│  ├─ 向量检索
│  └─ 混合检索（语义 + 向量，也是检索的一种方式）
└─ 增强生成
   ├─ 召回条数
   ├─ Re-ranking
   │  └─ 召回率
   └─ Top K
```

一段真实表达可能是：

```text
RAG 包括检索和增强生成
→ 检索有语义检索和向量检索
→ 两者混合就是混合检索
→ 回到增强生成：检索结果用来增强生成
→ 召回条数、Re-ranking、Top K
→ Re-ranking 这里还有召回率
```

正确的父链：

| 新节点 | 话语父节点 | 说明 |
| --- | --- | --- |
| 检索 | RAG | RAG 的组成部分 |
| 增强生成 | RAG | RAG 的组成部分 |
| 语义检索 | 检索 | 检索的方式 |
| 向量检索 | 检索 | 检索的方式 |
| 混合检索 | 检索 | 检索的一种方式，同时组合语义/向量 |
| 召回条数 | 增强生成 | 增强生成链路的参数 |
| Re-ranking | 增强生成 | 增强生成链路的阶段 |
| Top K | 增强生成 | 增强生成链路的参数 |
| 召回率 | Re-ranking | Re-ranking 的指标 |

这里必须区分两件事：

- **话语父链**：这句话从哪个节点延伸（学习路径，1→2→3）；
- **知识谓词**：这两个概念在语义上是什么关系（partOf/kindOf/measures…）。

当前实现把两者都压成 focus，所以多跳必然错。

### 6.3 为什么现在必然这样（代码核对）

已核对 `server/src/index.ts` 的 `/extract` 与 `providers/deepseek.ts`：

1. **一次抽取只有一个 focus**：`fromNodeId ?? root`；
2. **所有新节点围绕 focus 摆放**：`placeAround(..., focus)`；
3. **所有来源线从 focus 出发**：`focus → new node`，并有孤岛禁令兜底；
4. **关系 source 缺省为 focus**：`source = rel.source || focus`；
5. **prompt 只给"当前节点"**，没有"这句话里谁接谁/父节点链"字段；
6. **前端 `focusId` 抽取后不推进**：连续说话时焦点仍是初始节点；
7. **detect 与 extract 是两套独立结果**：ghost 按名字匹配，没有 ID/父节点/关系。

所以现象不是"模型没理解 RAG"，而是**数据模型里没有"这句话的父节点/多焦点状态"这个概念**，程序只能用全局 focus 兜底。

### 6.4 为什么 Ghost 不能解决

Ghost 当前是：

```text
检测候选 → 前端 ghost → final 重新 extract → 按名字匹配 ghost → 动画
```

它没有稳定 provisional ID、没有父节点、没有关系；final 会重新抽、改名字、改数量、改归属。**Ghost 是 UI 层补丁，多焦点是图状态问题，不在一个层。**

### 6.5 需要什么模型（先不写实现）

第一性原理上的必要结构：

```text
稳定 mention
  → provisional 实体（稳定 ID）
  → 从活跃焦点集合中选父节点（不是全局 focus）
  → 立即渲染 provisional 节点/父链
  → 异步关系验证
  → commit（同一 ID）
  → 失败/无关 → tombstone / 撤回
```

关键不变式：

1. **每个实体从第一次出现就有稳定 ID**：ghost 和正式节点是同一身份；
2. **每个实体有话语父节点**：与知识谓词分开；
3. **焦点是集合/栈，不是一个 cursor**：支持多分支、回退、随机跳转；
4. **关系候选覆盖同句新节点 + 已有节点**：不只对 focus；
5. **首次反应走本地快路径**：mention/别名匹配毫秒级，LLM 只做异步验证。

最小修复可以先做：

- focus cursor + parent 字段 + 关系候选扩展到同句/已有节点；
- 但这只能修星形图，修不了"多分支随机跳转"和速度；
- 目标架构需要 provisional 状态、revision、幂等、reconciliation。

### 6.6 参考研究

- 实时语音→图已有演示（[IJCAI 2020](https://ijcai.org/Proceedings/2020/777)），但只到关键词图；
- 对话建图的难点是回指、话题切换、跨轮上下文（[RPI 综述项目](https://tw.rpi.edu/project/towards-automatic-knowledge-graph-construction-dialogue)）；
- 多焦点需要经典话语焦点栈/注意力状态（Centering Theory）；
- 流式演化需要独立状态/修订机制（[LiveGraph](https://dl.acm.org/doi/10.1145/3786335.3813169) 方向）；
- 没有现成"教学语义 + 多焦点 + provisional"系统。

详见 [external-research.md](../reference/external-research.md) 第 6 节。

### 6.7 需要产品拍板

1. 一句话是否允许多个新节点、多跳（1→2→3）？
2. 父节点规则：最近引入实体 / 当前聚焦分支 / 显式线索 / 保留多个候选？
3. 用户跳回旧分支时，焦点栈怎么回退？
4. 关系不明确时：挂父节点（suggest） / 不建 / 等下一句？
5. 首次可见反应目标：mention <100ms、provisional <1s、commit 2–4s？

这 5 条不定，继续改 prompt 或 Ghost 都只是碰运气。


### 6.8 处理方案记录（2026-11-16）：渐进式 ghost + 本地快路径

目标不是把 3 秒压到 1 秒，而是：

> **用户说完一句，地图立刻有一个可见的 provisional 反馈；3 秒后再变成正确实体。**

#### 阶段

```text
稳定短语/mention
  → 本地 mention/别名匹配（已知节点：立即高亮）
  → 未知候选：先在当前焦点旁放一个 provisional 占位（“识别中…”）
  → 异步 LLM 抽取/父节点/关系
  → 占位填充为真实节点（同一 ID）
  → 失败/无关：淡出或进“待确认”
```

关键：**占位不是假节点**，它明确标为 provisional；不参与出题、副本、正式统计。

#### 父节点/焦点

- 维护活跃焦点集合（stack + salience），不是单 cursor；
- 每个 mention 选择父节点：显式线索 > 最近焦点 > 语义兼容；
- 不确定时保留多个父候选（suggest），不要静默丢；
- 用户跳回旧分支时，焦点栈回退。

#### 本地快路径

- 已知节点 mention：名称/别名精确匹配 + 拼音/模糊匹配，**不需要模型**；
- 语义近义/改写：可选小 embedding 模型（ONNX，30–100MB 量化），只做匹配，不做推理；
- 新概念/关系：云端 LLM 异步；
- 不为“快”在客户端塞大模型。

#### 为什么不是继续压延迟

- 3 秒是语义抽取的合理量级；
- 压到 1 秒需要换模型/牺牲质量，成本高；
- 用 provisional 先给反馈，是**隐藏延迟**，不是压缩延迟；
- 只要 provisional 状态清晰，用户能接受 3 秒后修正。

#### 待验证

1. provisional 占位的视觉是否像“假节点”；
2. 父节点猜错时，修正是否会造成闪烁；
3. 本地匹配的召回是否够（别名/Rerun 等 ASR 变体）；
4. 小 embedding 是否值得引入，还是词典+模糊足够。
