## 1. 节点准入：什么值得成为节点

### 问题

LLM 倾向于把一段话里的**所有名词**都识别成实体；但地图节点是学习对象，不是 mention。

典型错误：

- "RAG 和知识库的关系像白雪公主里后妈派猎人追杀公主一样" → 抽出白雪公主、猎人、公主、后妈；
- 工作流步骤被建成节点；
- 口头语、代词、玩笑被建成节点。

### 尝试

1. **纯 LLM 抽取**：能抽到，但无法判断"值不值得建"；
2. **角色过滤**（topic/subconcept/process/example/metaphor/step/noise）：
   - 能排除喻体/例子/步骤，但角色分类本身不稳；
   - 雪白句测试里，LLM 一度把 RAG 判成 metaphor/noise，需要 prompt 规则纠正；
3. **锚点优先**：先有已有节点作锚点，候选与锚点做关系快判；无关不建；
4. **关系优先准入**：没有有意义的关系就不建节点（用户明确引入的新主题例外）；
5. **MD-first 收敛**：节点 = 学习锚点 + MD；`type` 可选/可后补；领域细节写 MD，不新增节点/边。

### 当前处理

- 节点准入看四问：是话题主体/必需下位概念吗？可解释/可出题吗？有断言或证据吗？属于当前范围或用户明确引入吗？
- 比喻/例子/步骤不进节点；步骤进流程副本；
- 不强制类型；
- 关系判定允许 `unrelated`；没有证据不建正式关系；
- 主题节点可以"先建、关系待确认"。

### 未决

- 角色分类的准确率还不够，尤其是中文隐喻/否定/指代；
- "话题节点无关系先建"与"没关系不建节点"的边界；
- 没有稳定的节点准入评测集。

## 2. 关系方向：同一关系不能画反

### 问题

同一对概念，模型经常把方向画反：

- `partOf` 整体→部分 / 部分→整体混用；
- `prerequisite` 前置→后续画反；
- "A 包含 B" 直接存成 `contains`，不知道是 `partOf` 还是 `kindOf`。

### 尝试

- 固定方向表；
- 用证据句的实体顺序归一；
- 程序校验 + 置信度；
- 把"包含"映射到 `partOf`（部分→整体）或 `kindOf`（具体→上位），不新增谓词。

### 当前方向约定

| 谓词 | 方向 |
| --- | --- |
| `kindOf` | 具体 → 上位 |
| `partOf` | 部分 → 整体 |
| `prerequisite` | 前置 → 后续 |
| `contrast` | 无方向 |
| `related` | 无方向 |
| `alternative` | 旧 → 新 |

### 未决

- `partOf` 的传递性例外（部分的部分）；
- 同一对节点是否允许多谓词（建议最多 2，层级与 `related` 不相交）；
- 关系错误后的更正流程（正式关系不可删除）。

## 3. 谓词校验：`partOf` 万能化

### 问题

测试中"混合检索把 BM25 和向量召回合并"被全部判成 `partOf`：

- 混合检索不是 RAG 的一部分；
- BM25/向量召回是混合检索的组件，`partOf` 可以；
- Rerank 是阶段，更适合 `related(阶段)` 或 `prerequisite`。

模型倾向用一个谓词覆盖所有"有关联"的情况。

### 尝试

- prompt 里加谓词消歧规则：
  - "是一种" → `kindOf`；
  - "由…组成/包含组件" → `partOf`；
  - "使用/从…获取/来源" → `related(使用/来源)`，不要 `prerequisite`；
  - "组合了…" → `related(组合)`，不要 `partOf`；
- 证据/置信度门槛；
- 自由标签承载领域细节（衡量/组合/使用/阶段），不强行扩谓词。

### 当前处理

- 首版只保留 5 个核心谓词 + 可选 `alternative`；
- 领域语义先用 `related + label` 或节点 MD；
- 只有反复出现且需要程序推理时，才升级为一等谓词。

### 未决

- 包含句仍会把"混合检索"判成 `partOf`；
- 需要一套"部分/种类/前置/对比/无关"问题链，而不是一次自由 prompt；
- 谓词准确率基线 87%，但样本小。

## 4. 流式与延迟：怎样像"言出法随"

### 问题

- 当前 `/extract` 一次 3.9–5.0s（两次 LLM 调用，本地实测）；
- 逐对判关系不可接受（3 候选 × 2 锚点 × 1.5–2.5s ≈ 9–15s）；
- 句末才生成节点，用户感觉"说完才动"。

### 尝试

1. **锚点优先（A 方案）**：
   - 锚点 → 候选 → 快筛 → provisional → 慢判 → commit/修复；
   - 一次批量关系判定，目标 2–4.5s；
   - A1 严格（无关系不建）/ A2 话题优先（topic 先建、关系待确认）。
2. **角色优先（B 方案）**：
   - 先角色分类，再关系判定；
   - 没有直接证据，作为并列假设，未采用。
3. **MD-first**：
   - 不搞 15 谓词/6 类型重本体；领域细节进 MD/自由标签。
4. **流式 ghost**：
   - partial 匹配已有节点 → 高亮；
   - 每增长 6 字符 detect 一次 → 候选 ghost；
   - final 全量 detect → extract；
   - 新节点从 ghost 位置起飞到最终位置。

### 当前处理

```text
partial → 多步 detect → ghost
final → 全量 detect → 现有 /extract
extract 返回 → 新节点按名字匹配 ghost → 起飞动画
```

测试结果：

| 场景 | 结果 |
| --- | --- |
| 雪白句 A1 | 不建 RAG；白雪公主等排除；总 2.4s（预置候选） |
| 雪白句 A2 | 只建 RAG；无类比正式关系 |
| 检索句 | RAG + `related(使用/检索)` |
| 包含句 | 5 节点；混合检索仍 `partOf`（错） |
| 端到端（含抽取） | 2.8–4.6s；流式 final 补检后约 6–9s |

### 未决

- ghost 只是前端预览，不是 provisional 实体；
- detect 与 extract 是两条链路，结果可能不一致；
- final 补检 + extract 串行，延迟损害"言出法随"；
- 没有确认/拒绝/修复/重新映射；
- 没有真正逐词/逐实体提交。

## 6. 核心问题：不是单 Focus，而是缺少话语状态模型（2026-11-16）

### 6.1 最初看到的现象

1. 说话时地图反应不够快，ghost 不够连续；
2. ghost 和最终实体接不上，候选消失后节点像另起；
3. 空白图谱里一句话生成 3 个节点，3 个都围绕同一个核心节点；
4. 用户说 1 → 2 → 3，系统只判断 2、3 和 1 的关系，2 和 3 都挂到 1。

这些是表层现象。继续往下挖，真正的问题不是"focus 不准"，而是**系统没有多焦点/父链这个数据模型**。

### 6.2 真正的问题：多焦点与父链

真实对话会不断切换焦点。以 RAG 为例：

```text
RAG
├─ 检索
│  ├─ 语义检索
│  ├─ 向量检索
│  └─ 混合检索（语义 + 向量，也是检索的一种方式）
└─ 增强生成
   ├─ 召回条数
   ├─ Re-ranking
   │  └─ 召回率
   └─ Top K
```

一段真实表达可能是：

```text
RAG 包括检索和增强生成
→ 检索有语义检索和向量检索
→ 两者混合就是混合检索
→ 回到增强生成：检索结果用来增强生成
→ 召回条数、Re-ranking、Top K
→ Re-ranking 这里还有召回率
```

正确的父链：

| 新节点 | 话语父节点 | 说明 |
| --- | --- | --- |
| 检索 | RAG | RAG 的组成部分 |
| 增强生成 | RAG | RAG 的组成部分 |
| 语义检索 | 检索 | 检索的方式 |
| 向量检索 | 检索 | 检索的方式 |
| 混合检索 | 检索 | 检索的一种方式，同时组合语义/向量 |
| 召回条数 | 增强生成 | 增强生成链路的参数 |
| Re-ranking | 增强生成 | 增强生成链路的阶段 |
| Top K | 增强生成 | 增强生成链路的参数 |
| 召回率 | Re-ranking | Re-ranking 的指标 |

这里必须区分两件事：

- **话语父链**：这句话从哪个节点延伸（学习路径，1→2→3）；
- **知识谓词**：这两个概念在语义上是什么关系（partOf/kindOf/measures…）。

当前实现把两者都压成 focus，所以多跳必然错。

### 6.3 为什么现在必然这样（代码核对）

已核对 `server/src/index.ts` 的 `/extract` 与 `providers/deepseek.ts`：

1. **一次抽取只有一个 focus**：`fromNodeId ?? root`；
2. **所有新节点围绕 focus 摆放**：`placeAround(..., focus)`；
3. **所有来源线从 focus 出发**：`focus → new node`，并有孤岛禁令兜底；
4. **关系 source 缺省为 focus**：`source = rel.source || focus`；
5. **prompt 只给"当前节点"**，没有"这句话里谁接谁/父节点链"字段；
6. **前端 `focusId` 抽取后不推进**：连续说话时焦点仍是初始节点；
7. **detect 与 extract 是两套独立结果**：ghost 按名字匹配，没有 ID/父节点/关系。

所以现象不是"模型没理解 RAG"，而是**数据模型里没有"这句话的父节点/多焦点状态"这个概念**，程序只能用全局 focus 兜底。

### 6.4 为什么 Ghost 不能解决

Ghost 当前是：

```text
检测候选 → 前端 ghost → final 重新 extract → 按名字匹配 ghost → 动画
```

它没有稳定 provisional ID、没有父节点、没有关系；final 会重新抽、改名字、改数量、改归属。**Ghost 是 UI 层补丁，多焦点是图状态问题，不在一个层。**

### 6.5 红队后的取舍与最终方案（2026-11-16）

#### 6.5.1 红队结论

方向对，但 MVP 过度设计了：

1. 把"生产期问题"（持久化、并发、三层一致、完整实体消解、通用 benchmark）提前成了门槛；
2. 把"研究级模型"（完整焦点栈、SDRT/QUD）当成了 MVP 必需；
3. 把"Ghost"做成了 preview 层，导致它可能和最终结果不一致——这是实现错误，不是需求错误。

**需求本身没问题：用户要的是"很快的反馈 + 言出法随的感觉"。错的是把 Ghost 做成另一条链路。**

#### 6.5.2 取舍表：原本可能测什么，现在实际用什么

| 方向 | 原本可能测试 | 现在实际使用 | 不用的理由 | 什么时候回来 |
| --- | --- | --- | --- | --- |
| 本地 mention 匹配 | 名称/别名/拼音/模糊 | ✅ 名称 + 别名 + 模糊 | 够用、零模型 | 召回不足时加小 embedding |
| 小 embedding | 语义近义匹配 | ❌ 暂不用 | 30–100MB，先不引入 | 本地匹配漏召回时 |
| 完整实体链接/消解 | 跨轮多名称合并 | ❌ 暂不用 | 现有节点别名够 | 跨轮歧义/重名严重时 |
| 简单活跃焦点 | 最近焦点 + 显式线索 | ✅ 用 | 能覆盖 RAG 例子的父链 | 父节点错误率高时 |
| 完整焦点栈/SDRT/QUD | 多分支、随机跳转、回退 | ❌ 暂不用 | 研究级；MVP 用近似 | 简单焦点不够时 |
| provisional 持久化 | 刷新/重连保留 | ❌ 暂不用 | 单端内存够 | 需要跨会话/多端 |
| revision/tombstone | 撤销、版本、正式纠错 | ❌ 暂不用 | 正式关系不可删；provisional 只需替换 | 需要审计/正式纠错 |
| 三层一致性/版本号/幂等 | 前端/后端/LLM 一致 | ❌ 暂不用 | 单用户单端 | 持久化/多端/重试 |
| 并发控制/Saga/CRDT | 并发写、补偿、离线 | ❌ 暂不用 | 同上 | 多端/离线 |
| 通用教学图 benchmark | 大规模评测 | ❌ 不用 | 我们给不出，也不该是门槛 | 有标注集后再做 |
| 每词实时正确建图 | 逐词生成 | ❌ 不承诺 | 新概念必须等 LLM | 不承诺 |
| 云端 LLM 抽取 | 概念/关系/证据 | ✅ 用 | 现有能力 | 持续评测 |

#### 6.5.3 最终方案：Ghost 不是 preview，是 provisional 实体本身

一句话：

> **用户说完一句，地图上立刻出现一个 provisional 节点；它不是"预览影子"，而是最终节点的早期状态。后续只更新它，不另起一个节点。**

```text
已知 mention
  → 本地匹配 → 已有节点高亮（不新建）

未知 mention
  → 创建 provisional 节点（稳定 provisionalId）
  → 立即渲染：占位名/“识别中”/父候选
  → 异步 LLM 抽取
  → 填充同一个 provisionalId：名字/定义/父节点/关系
  → 有证据 → commit 为正式节点（同一个 ID）
  → 无证据/无关 → 淡出 / 标记“已修正”
```

必须遵守：

1. **同一个 ID**：provisional 和最终节点是同一个实体，不能按名字二次匹配；
2. **同一套状态**：没有"detect 结果"和"extract 结果"两套真相；
3. **修正可见**：如果父节点/名字变了，动画显示"正在修正"，不能静默替换；
4. **provisional 不参与**出题、副本、正式统计；
5. **父节点是候选**：不确定时显示多个父候选或 `suggest`，不静默选一个。

#### 6.5.4 父节点：MVP 用简单活跃焦点

不建完整话语栈，先用：

```text
activeFocus = [最近提到的已有节点, 最近创建的 provisional 节点, 当前显式话题]
```

每个新 mention：

1. 有显式线索（包括/分为/其中/回到/另一方面）→ 按线索选；
2. 否则选最近、且类型/语义兼容的 activeFocus；
3. 不确定 → 保留 2 个父候选，关系用 suggest；
4. 用户跳回旧分支 → 把旧节点重新提到 activeFocus 前面。

这不是完整多焦点理论，但足以先验证 RAG 例子。

#### 6.5.5 速度与"言出法随"

| 阶段 | 目标 | 手段 |
| --- | --- | --- |
| 已有节点高亮 | <100ms | 本地名称/别名/模糊 |
| provisional 出现 | <300ms | 本地占位，不调 LLM |
| 填充名字/父节点 | 1–3s | 异步 LLM |
| commit 正式节点 | 2–4s | 证据校验后 |

不承诺"每个词立刻正确建图"；承诺"每个稳定 mention 立刻有反馈，随后修正"。

#### 6.5.6 Ghost "撒谎 UI" 的修正

之前错在：

```text
detect ghost → final 重新 extract → 按名字匹配 → 动画
```

这是两条链路，必然可能不一致。

修正后：

```text
provisional 节点（ID）→ 异步填充同一个 ID → commit
```

如果最终结果与 provisional 不同：

- 名字变 → 同节点标签 morph；
- 父节点变 → 边动画迁移；
- 不成立 → 淡出并标"已修正"；
- 不允许"旧 ghost 消失、另一个新节点出现"。

验收标准：

1. 一个 mention 不能出现两个节点；
2. provisional 和最终节点 ID 相同；
3. 修正时用户能看见"正在修正"，而不是静默变化。

#### 6.5.7 验收：只用 RAG 场景，不用通用 benchmark

输入：

```text
RAG 包括检索和增强生成
→ 检索有语义检索和向量检索
→ 两者混合就是混合检索
→ 回到增强生成：检索结果用来增强生成
→ 召回条数、Re-ranking、Top K
→ Re-ranking 这里还有召回率
```

期望父链：

| 新节点 | 父节点 |
| --- | --- |
| 检索 | RAG |
| 增强生成 | RAG |
| 语义检索 | 检索 |
| 向量检索 | 检索 |
| 混合检索 | 检索 |
| 召回条数 | 增强生成 |
| Re-ranking | 增强生成 |
| Top K | 增强生成 |
| 召回率 | Re-ranking |

验收只看：

- 父链是否大致正确；
- provisional 是否立刻出现；
- 修正是否可见；
- 是否不再全部挂 RAG。

不要求通用教学图 benchmark。

#### 6.5.8 什么时候返回来换方向

| 触发 | 回来做什么 |
| --- | --- |
| 本地匹配漏召回 | 加小 embedding |
| 父节点错误率高 | 上完整焦点栈/线索模型 |
| 修正闪烁严重 | 重新设计 provisional 状态/动画 |
| 需要刷新保留 | 上持久化 |
| 需要正式纠错/审计 | 上 revision/tombstone |
| 多端/并发 | 上版本/幂等/Saga |
| 需要大规模评测 | 再建标注集 |

**当前就按 6.5.3 的 provisional 同 ID 方案做，不再用"preview ghost + 二次 extract"。**


### 6.6 参考研究

- 实时语音→图已有演示（[IJCAI 2020](https://ijcai.org/Proceedings/2020/777)），但只到关键词图；
- 对话建图的难点是回指、话题切换、跨轮上下文（[RPI 综述项目](https://tw.rpi.edu/project/towards-automatic-knowledge-graph-construction-dialogue)）；
- 多焦点需要经典话语焦点栈/注意力状态（Centering Theory）；
- 流式演化需要独立状态/修订机制（[LiveGraph](https://dl.acm.org/doi/10.1145/3786335.3813169) 方向）；
- 没有现成"教学语义 + 多焦点 + provisional"系统。

详见 [external-research.md](../reference/external-research.md) 第 6 节。

### 6.7 需要产品拍板

1. 一句话是否允许多个新节点、多跳（1→2→3）？
2. 父节点规则：最近引入实体 / 当前聚焦分支 / 显式线索 / 保留多个候选？
3. 用户跳回旧分支时，焦点栈怎么回退？
4. 关系不明确时：挂父节点（suggest） / 不建 / 等下一句？
5. 首次可见反应目标：mention <100ms、provisional <1s、commit 2–4s？

这 5 条不定，继续改 prompt 或 Ghost 都只是碰运气。
