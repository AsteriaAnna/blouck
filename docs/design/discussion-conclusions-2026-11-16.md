# 讨论结论记录：节点、关系与流式生成（2026-11-16）

性质：讨论结论与待决策清单，不是已确认实现。
相关文档：
- `docs/design/three-hard-problems-solutions.md`（方案思考、延迟实测、ghost 层）
- `docs/reviews/relation-extraction-papers.md`（论文清单）
- `docs/design/required-implementation.md`（需求基线）

---

## 1. 原始问题

1. 开源项目的"节点"和我们的"节点"到底差在哪？我们还需要什么？
2. 如果同步判断两个节点的关系、无关就不连线，能不能解决？
3. 用户边说，节点能不能边生成？卡点在哪？
4. 关系识别方案是不是还没定？需要讨论。

---

## 2. 已达成的共识

### 2.1 节点不是实体，是学习资产

| 维度 | 开源实体/记忆节点 | 我们的节点 |
| --- | --- | --- |
| 语义 | 实体/记忆事实 | 学习对象（概念/方法/组件/指标/过程） |
| 粒度 | mention 就建 | topic/subconcept/process 才建；example/metaphor/step/noise 不建 |
| 内容 | 属性/事实 | 节点 MD（理解、疑问、类比、资料、关系定位） |
| 状态 | 时间有效性/检索分 | tier、题目、方向、frontier、隐藏/争议 |
| 下游 | 检索/问答 | 出题、三档、副本、地图生长 |
| 所有权 | 系统记忆 | 用户学习资产（可改、可纠错） |
| 错误成本 | 检索噪声 | 学错/题错/副本错/地图污染 |

**结论：开源节点是"指针/事实锚点"，我们的节点是"带学习闭环的卡片"。**

### 2.2 关系优先准入（relation-gated admission）方向正确

- 不是"建节点后再判断是否连线"，而是"**没有有意义的关系，就不建节点**"；
- 例外：用户明确要学的新主题（user-introduced）、初始节点；
- 比喻/例子 → 节点 MD；步骤 → 流程副本；噪声 → 丢弃；
- 这样能同时解决"假关系"和"节点污染"。

### 2.3 "无关"必须是一等输出

- 关系判定必须允许 `unrelated / unknown`；
- 没有证据默认不建正式关系；
- 不能只做"有没有关系"的二元判断，还要谓词、方向、证据、置信度。

### 2.4 流式：ghost-first，而不是逐词提交

- L1：边说边出现 ghost 候选/已有节点高亮（本地匹配，<100ms–1s）；
- L2：句末/停顿 → 一次抽取 + 一次批量关系判定 → 正式节点（2–4s）；
- L3（每个 partial/每个词都成为正式节点）：**不现实**；
- 卡点：ASR partial 不稳、语义单位未完成、LLM 延迟、图抖动、成本。

### 2.5 延迟结论

- 当前 `/extract` 实测 3.9–5.0s（两次 DeepSeek 调用，本地环境）；
- 逐对 LLM 判定不可接受（3 候选×2 锚点×1.5–2.5s ≈ 9–15s）；
- 可行方案：候选剪枝 top 1–3 + **一次批量关系判定** + 异步提交，目标 2–4.5s；
- 方向生成延后/合并，避免阻塞主链路。

## 3. 尚未决定的问题（需要讨论/实验）

### 3.1 关系识别方案（核心未决）

目前有三个候选，**还没有定**：

| 方案 | 做法 | 优点 | 风险 |
| --- | --- | --- | --- |
| A. 生成式单次抽取（现状） | 一句话 → LLM 输出 entities/relations | 简单、覆盖快 | 无法判断无关、虚假关联、方向不稳 |
| B. 成对判定（LLM judge） | 给定锚点+候选+证据，输出谓词/方向/无关/置信度 | 可控、可解释、能拒答 | 需要证据检索、批量设计、仍有虚假关联 |
| C. 分类器 + LLM 校验 | 先用 RE 模型（GLiREL/DeepKE）出候选，再 LLM 校验 | 速度/召回可能更好 | 中文/方向/许可证/维护成本 |
| D. 混合 | 候选生成（本地小模型）→ 成对 LLM 判定 → 程序校验 | 平衡 | 工程复杂，需要评测 |

**未决点：**

1. 用生成式抽取、成对判定、分类器，还是混合？
2. 关系判定的输入：只用当前句？+节点 MD？+历史转写？+外部搜索？
3. 是否要求每个关系都有原文证据？外部搜索证据算不算？
4. 置信度阈值、是否允许弃权、低置信是否进虚线/待确认？
5. 关系方向由模型直接输出，还是模型给谓词+证据、程序归一？
6. 同一对节点允许多少种谓词？冲突怎么处理？

### 3.2 关系 schema 未最终定稿

- 六类谓词（kindOf/partOf/prerequisite/contrast/alternative/related）是否固定？
- `analogy/example` 作为"非知识关系"只进 MD，是否确认？
- "包含"不单独作为谓词，映射到 partOf/kindOf，是否确认？
- 是否需要 `contains`、`instanceOf`、`causes` 等扩展？

### 3.3 锚点规则未定

- 是否强制"必须提到地图里的一个已有节点"才能生成？
- 用户没说已有节点时：用当前 focus 兜底？询问？进候选层？
- 一句话提到多个已有节点：选一个锚点还是多锚点？
- 用户明确引入新主题（"我想学 BM25"）时，允许无关系建节点吗？

### 3.4 ghost 层未定

- ghost 何时出现（partial 命中词典/候选抽取完成）？
- ghost 何时转正式（ASR final / 静音 / 句末标点 / 置信度）？
- ghost 被 ASR 修订时如何替换/撤回？
- ghost 是否可点击、可出题（建议：不可以）？
- ghost 的 UI 表达（半透明、虚线、加载态）？

### 3.5 评测未定

- 关系判断的 gold 集怎么建（多少对、谁标、方向/证据/无关如何标）？
- 指标：谓词准确率、方向合法率、无关召回、证据覆盖率、延迟；
- 目标阈值：关系 P/R、方向合法率、无关误判率。

## 4. 下一步建议

### 4.1 先做关系识别决策实验（不改架构）

用 100 对节点（含 30 对无关、20 对方向敏感、20 对包含/归类、30 对普通关系），对比：

1. A：单句生成式抽取（现状）；
2. B：成对 LLM 判定（名称+定义+证据，输出谓词/方向/无关/置信度）；
3. C：RE 分类器候选 + LLM 校验（如 GLiREL/DeepKE，需验证中文与许可）。

指标：

- 谓词准确率；
- 方向合法率；
- 无关判断准确率/误判率；
- 证据覆盖率；
- P50/P95 延迟；
- 每条判定成本。

### 4.2 再决定是否引入 ghost 层

如果 B/C 在离线实验里达到可接受准确率，再做 L1 ghost 原型：

- partial 命中已有节点 → 高亮/ghost（不调 LLM）；
- final → 批量判定 → 提交；
- 测 time-to-first-ghost、time-to-commit、churn rate。

### 4.3 产品需要拍板

1. 关系 schema（六类 + analogy/example 注释）；
2. 锚点规则（严格/兜底/新主题例外）；
3. 关系判定方案（A/B/C/D）；
4. 置信度/虚线/待确认策略；
5. 是否允许外部搜索作为证据。

## 5. 一句话总结

**节点是学习资产，不是实体；关系是准入门槛，不是事后连线；流式体验靠 ghost 层，不靠逐词提交；关系识别方案（A/B/C/D）还没定，必须用 100 对实验数据拍板。**

## 6. 补充讨论：两阶段写入 + 修复（乐观写入）方案评估

> **证据等级说明（2026-11-16 修正）：** 本节与 §7 中的“角色过滤、三态 possible/unrelated/defer、ghost/provisional、两阶段修复”等，**是设计假设，不是任何开源项目的默认实现**；只有少数环节有开源/论文依据。逐条证据见 §8。不要把这些当作既定流程。

用户提出：

> 流式先快速判断两个东西有没有关联（如 RAG 与灰姑娘，第一次判断没关系 → 不建节点）；
> 如果 RAG 和另一个词第一轮感觉有关系 → 先放行节点；
> LLM 后面按规则再检查，发现关系不准确就调整；
> 如果误判，查有没有相关节点：有就关联，没有就让它孤立、可删除；
> 再来一轮规则判断；
> 同时生成新节点的探索方向，以及和现有节点的推荐解锁关联。

### 6.1 方案本质

这是**乐观写入（optimistic write）+ 事后修复（reconciliation）**：

```text
快速第一轮 → 先放行/先不拦
慢速第二轮 → 用证据+规则校验
发现错误 → 重连/孤立/撤回
```

和数据库的"先写后校验、失败补偿"、 speculation、eventual consistency 是同一类思路。**方向正确，能显著降低用户等待。**

### 6.2 它解决的痛点

1. **不用等慢判定**：先给用户"疑似节点"的即时反馈；
2. **减少误杀**：第一轮拿不准的可以先放行，后面修；
3. **关系优先准入**：第一轮就有"是否可能相关"的门槛；
4. **可修复**：发现误判后重连/孤立，而不是一错到底；
5. **并行收益**：探索方向、推荐关联可以在等待期生成。

### 6.3 必须修正的 5 个点

#### 修正 1：第一轮不能"判死没关系"，只能"暂缓/不确定"

快速判定（本地/小模型）一定有假阴性。如果第一轮判"没关系"就永久不建节点，会漏掉正常学习。

正确状态：

```text
possible（可能相关） / unrelated（明确无关） / defer（拿不准）
```

- `possible` → 进 provisional（临时节点）；
- `unrelated` → 只有**慢速第二轮**才能下这个结论；
- `defer` → 候选层/笔记，不直接上地图。

**第一轮只做"粗筛"，不做最终判决。**

#### 修正 2：provisional 节点不是正式节点

"先放行节点"必须是 **ghost/候选节点**，不是正式节点：

- 不写正式节点表（或写 `status=provisional`）；
- 不出题、不参与三档、不参与副本、不计入统计；
- UI 上半透明/虚线，可撤回；
- 慢速校验通过后才 `commit` 为正式节点。

**不能先建正式节点、再删除。**

#### 修正 3："可删除"与基线冲突，应改为"墓碑/软删除"

业务基线明确：**不提供节点删除，只提供隐藏**。

建议区分三种：

| 对象 | 处理 |
| --- | --- |
| 从未 commit 的 provisional 节点 | 直接丢弃（用户没看过/或标记为已移除） |
| 已 commit 但后来判定关系不成立 | **不硬删除**；标 `tombstone/hidden`，保留历史与来源；地图不显示 |
| 用户主动隐藏 | 按基线：整片隐藏 + 可撤回 |

如果产品确实要硬删除，必须单独定义：二次确认、导出、恢复、历史记录。**默认不要硬删除。**

#### 修正 4：修复要处理"依赖物"

一个 provisional 节点可能已经带出：

- 关系（临时边）；
- 方向（临时方向）；
- 推荐关联（虚线建议）；
- 副本候选（不应在 provisional 阶段生成）。

修复时必须级联：

- 关系不成立 → 临时边撤回；
- 方向失效 → 归档；
- 推荐关联 → 移除/重算；
- 副本 → 不生成（provisional 不参与）。

需要 `graphVersion/taskId` 防止旧结果覆盖新状态。

#### 修正 5：方向和推荐放在 commit 之后，或标 provisional

"同时生成探索方向和推荐解锁关联"可以，但要：

- 方向：正式节点 commit 后再生成，或生成后标 provisional；
- 推荐关联：只作为**虚线建议/推荐**，不自动建正式边；
- 推荐解锁：由 tier/前置条件决定，不能因为 provisional 就解锁副本。

### 6.4 建议的状态机

```text
observed（听到 mention）
  → candidate（候选，未上地图）
    → provisional（可能相关，ghost 显示）
      → verified（慢速校验通过，commit 正式节点 + 关系）
      → relinked（校验发现应连到另一个已有节点）
      → tombstoned（校验确认无关/重复；soft delete）
    → note（比喻/例子/步骤，不进图）
    → dropped（噪声/第一轮明确无关）
```

关系也有状态：

```text
candidate relation → provisional relation → verified formal / suggested / removed
```

### 6.5 时间/成本

| 阶段 | 方案 | 目标 |
| --- | --- | --- |
| 第一轮粗判 | 本地 embedding/词典/小分类器 | <100ms–1s |
| provisional 显示 | ghost 节点/临时边 | 立即 |
| 第二轮校验 | 一次批量 LLM（top 1–3 候选） | 1.5–2.5s |
| commit/修复 | 程序校验 + 写库 | <100ms |
| 总感知 | 用户看到 ghost → 正式 | 2–4s |

两轮会增加成本，但第一轮用本地小模型，成本可控；**关键是批量第二轮，不要逐对调用**。

### 6.6 这个方案的风险

1. **用户看到节点又消失**：ghost 必须视觉上区分，且不要频繁闪；
2. **第一轮假阴性**：用 defer 而不是 unrelated；
3. **修复风暴**：限制轮次（最多 2–3 轮），避免无限重判；
4. **状态不一致**：provisional 不参与题目/副本/统计；
5. **删除争议**：默认软删除 + 历史，不硬删；
6. **推荐误连**：推荐只做虚线建议，用户确认才正式。

### 6.7 结论

**方案方向正确，建议采用"两阶段 + 修复"作为流式关系生成的主架构：**

- 第一轮：快速粗判（possible/unrelated/defer），只生成 ghost；
- 第二轮：批量成对校验（证据 + 谓词/方向 + 无关），通过才 commit；
- 修复：误判 → 重连/墓碑/撤回，级联处理方向/推荐；
- 方向/推荐在 commit 后或标 provisional；
- 不做硬删除，默认软删除/隐藏；
- 最多 2–3 轮，避免修复风暴。

**一句话：不是"先建正式节点再删"，而是"先 ghost、再校验、再 commit、失败修复"。**

## 7. 示例推演：知识库 + RAG + 白雪公主

### 7.1 输入

> "我感觉 RAG 和知识库的关系就像白雪公主里那个派猎人去追杀公主的后妈一样。"

图谱里已有：**知识库**。

### 7.2 先区分三层，不要混在一起

| 层 | 这句话里有什么 |
| --- | --- |
| mention（识别到） | 知识库、RAG、白雪公主、猎人、公主、后妈 |
| role（角色） | 知识库=已有概念；RAG=话题/新概念；白雪公主/猎人/公主/后妈=比喻喻体（metaphor） |
| node（建不建） | 只可能建 RAG；知识库已存在；白雪公主等**不建** |
| relation（关系） | RAG 与知识库：这句话只是**类比**，没有断言事实关系 → `analogy/unknown`，不建正式知识边 |

**关键：不是"拿知识库去和后面所有词匹配关系"，而是先用角色把喻体过滤掉。**
白雪公主等词不是因为"和知识库无关"被排除，而是因为**它们不是学习对象**（role=metaphor）。

### 7.3 你说的"匹配所有词"为什么不对

如果直接做"知识库 ↔ 白雪公主/猎人/公主/后妈"的关系判断：

- 要跑 4–5 次无意义的关系判定；
- LLM 可能把"后妈派猎人追杀公主"硬解释成某种关系（虚假关联）；
- 即使判成无关，也浪费了调用，且没有解决"它们本来就不该建节点"的问题；
- 还可能漏掉"RAG 与图谱里其他已有节点"的关系（不只知识库）。

正确顺序是：

```text
mention
  → 角色判定（topic/subconcept/process/example/metaphor/step/noise）
  → 只对 topic/subconcept/process 做"与已有节点/焦点"的关系判定
  → 比喻/例子/步骤/噪声直接分流，不进入关系判定
```

### 7.4 "LLM 倾向判断有关"这个观察对不对？

对，而且有论文依据：

- ACL 2024 *Unexpected Phenomenon: LLMs' Spurious Associations in Information Extraction*：即使给定标签与原文语义无关，LLM 仍能把实体对套上关系；
- 所以"LLM 说有关"不能全信。

但"LLM 说无关"也不能当成绝对真理：

- 模型可能因为缺少上下文/证据而误判无关（false negative）；
- 不同模型/提示的偏置不同；
- 所以"无关"更适合做**高精度快速否决**，而不是最终判决。

建议的三态：

```text
possible（可能有关） / unrelated（明确无关） / defer（拿不准）
```

- 第一轮快判：`unrelated` 可以用来过滤明显噪声，但只对**非主题候选**；
- 第二轮慢判：结合证据、谓词、方向再下结论；
- `defer` 不丢，进候选/待确认。

### 7.5 这句话的正确输出（建议）

| 词 | 角色 | 建节点？ | 关系 |
| --- | --- | --- | --- |
| 知识库 | 已有概念 | 否（已存在） | — |
| RAG | topic | **是**（新节点） | 与知识库：`unknown/analogy`，不建正式知识边 |
| 白雪公主 | metaphor | 否 | 写进 RAG 节点 MD 的"类比"区 |
| 猎人 | metaphor | 否 | 同上 |
| 公主 | metaphor | 否 | 同上 |
| 后妈 | metaphor | 否 | 同上 |

RAG 节点可以有：

- 一条**探索来源线**（知识库 → RAG，表示"从当前节点延伸"）——这不是知识关系，只保证不是孤岛；
- 节点 MD 记录："用户类比：RAG 与知识库的关系，像白雪公主里后妈派猎人追杀公主"；
- 与知识库的正式关系：**先不建**（证据只是类比，不是事实断言）；如果后续用户说"RAG 从知识库检索资料"，再建正式关系。

### 7.6 后续慢速 LLM 精准检查

对 RAG 与已有节点做成对判定：

1. **RAG ↔ 知识库**：有没有事实关系？
   - 证据只有类比 → `unknown/analogy`，不建正式边；
   - 如果别处有"RAG 使用知识库"的证据 → 再建（如 `partOf/related`，按语义）。
2. **RAG ↔ 其他已有节点**：用 embedding/邻接检索 top-k，逐个判；
   - 有证据 → 正式/建议；
   - 无证据 → 建议（虚线）或不建。
3. **推荐解锁关联**：只做虚线建议，用户确认后才转正式；不因为 provisional 就解锁副本。

### 7.7 一个产品决策需要拍板

**"话题节点可以暂时没有知识关系吗？"**

- 如果必须"有关系才建节点"：RAG 在这句话里只有类比，可能不建；用户会觉得"我提到了 RAG，为什么没有？"
- 如果允许"话题节点先建、关系待确认"：RAG 建节点 + 来源线 + MD 类比，知识关系留空/待确认；更符合学习体验。

我建议：**允许 topic 节点在"关系未知"时建立，但必须标记"关系待确认"，且不参与出题/副本，直到有关系或用户确认。**

### 7.8 结论

- 这句话的正确结果不是"知识库与 4 个词判无关"，而是**角色过滤掉 4 个喻体，只保留 RAG 一个候选**；
- 关系判定只发生在 RAG 与已有节点之间；
- 类比只进 MD，不建正式关系；
- "无关"可以作为快速否决信号，但不能替代角色判定，也不能保证绝对正确；
- 话题节点可以"先建、关系待确认"，但要有明确状态和后续校验。

---

*本节用具体例子说明：识别 ≠ 建节点；角色过滤应先于关系匹配；类比不是知识关系。*

## 8. 证据审计：哪些有开源/论文依据，哪些是我的推断

### 8.1 有开源/论文依据的部分

| 步骤/结论 | 依据 | 说明 |
| --- | --- | --- |
| 从每个 chunk/episode 抽实体与关系 | GraphRAG、Graphiti、REBEL、DeepKE | 主流做法，但都是"抽 mention/关系"，不是"学习节点准入" |
| 实体去重/规范化/合并 | Graphiti | 有 entity resolution / dedupe；不判断教学角色 |
| "无关系"可以作为关系标签 | DocRED/TACRED 类 RE 数据有 `no relation`/`NONE`；DocRE None-class 论文 | 支持"输出无关"，但不等于我们的三态/弃权 |
| 先剪枝候选实体对，再给 LLM | *LLM with Relation Classifier for Document-Level Relation Extraction*（[arXiv 2408.13889](https://arxiv.org/abs/2408.13889)） | 明确支持"先筛可能有关系的 pair，再让 LLM 判" |
| LLM 倾向"硬找关系" | *Unexpected Phenomenon: LLMs' Spurious Associations in Information Extraction*（[ACL 2024](https://aclanthology.org/2024.findings-acl.545/)） | 支持"有关判断不可全信、需要标签验证" |
| 增量 episode + provenance + 时间有效性 | Graphiti | 支持"增量写入/来源"，不支持我们的教学角色 |
| 实体显著性/话题性 | 对话实体 salience 研究（如 Sussex 报告） | 支持"不是所有实体都同等重要"，但没有我们的角色分类 |
| 概念图抽取本身很难 | ACL 2025 Concept Map Extraction（F1 25–28） | 支持"需要评测与人工兜底" |

### 8.2 没有开源实现/论文直接证明，属于我的设计推断

| 步骤/结论 | 状态 | 需要验证什么 |
| --- | --- | --- |
| **角色分类**（topic/subconcept/example/metaphor/step/noise）作为节点准入门槛 | ❌ 无直接开源实现 | LLM 能否稳定区分角色；中文准确率；误杀率 |
| **先角色过滤，再做关系匹配** | ⚠️ 逻辑推断（不是某项目做法） | 对比"先匹配再过滤"与"先过滤再匹配"的成本/准确率 |
| **"无关"作为高精度快速否决** | ⚠️ 部分依据（虚假关联论文只说"有关"偏置） | 需要校准：无关判断的 precision/recall |
| **三态 possible/unrelated/defer** | ❌ 无直接依据；RE 里通常只有 no-relation 类 | defer 是否有效、是否值得引入 |
| **relation-gated admission**（没关系就不建节点） | ❌ 无直接开源实现 | 对比"允许 topic 无关系"与"严格有关系才建"的效果 |
| **ghost/provisional 节点** | ⚠️ 通用 UI/DB 模式（optimistic UI），非 KG 项目证明 | 用户是否接受 ghost； flicker/撤回成本 |
| **两阶段乐观写入 + 修复** | ❌ 无 KG 开源实现；属于系统设计 | 修复率、级联复杂度、旧结果覆盖、成本 |
| **tombstone/软删除** | ⚠️ 产品基线要求，不是开源技术 | 产品决策 |
| **方向/推荐在 commit 后生成** | ⚠️ 由 KST/QG 研究间接支持，非现成管线 | 延迟与质量 |

### 8.3 结论

- **没有一套开源项目完整证明"角色过滤 → 三态 → ghost → 两阶段修复"这条流水线**；
- 有依据的是**组件级**能力：抽取、去重、无关系类、候选剪枝、LLM 正偏置、增量 provenance；
- 我之前把"设计推断"写成"默认流程"是不对的；
- 正确做法：**把这条流水线标为假设，先用小实验验证，再决定是否采用**；
- 在验证前，不应把它写进需求基线或实现默认。

### 8.4 建议的最小验证（只验证假设，不默认）

| 假设 | 实验 | 指标 |
| --- | --- | --- |
| LLM 能区分角色 | 30 句含比喻/例子/步骤/噪声，人工标角色 | 角色准确率、误建率 |
| 角色过滤先于关系匹配更省 | 同一批句子两种顺序对比 | 调用次数、延迟、准确率 |
| "无关"高精度 | 50 对含无关/有关系对 | 无关 precision/recall |
| 三态 defer 有用 | 对比二态 vs 三态 | 误杀率、待确认量 |
| ghost 提升体感 | 20 句流式原型 | time-to-first-ghost、churn、用户评价 |
| 两阶段修复可维护 | 模拟错误关系修复 | 修复率、级联错误、成本 |

**只有实验通过，才把这些步骤升级为默认流程。**

## 10. 两个方法的完整定义（定稿记录）

> 本节把两种候选流程完整写下来，作为并列假设；**都不是已确认默认流程**，需实验对比后再选。
> 证据等级沿用 §8：有依据的标 ✅，推断/待验证的标 ⚠️/❌。

### 10.1 方法 A：锚点优先 + 快速无关过滤 + 慢速校验 + 修复

**一句话：** 先从已有节点（锚点）出发，快速筛掉明显无关的词，疑似相关的先放 provisional，再用 LLM 精准判定，错了再修。

**流程：**

```text
A1. 确定锚点
    - 当前 focus 节点；或用户这句话里提到的已有节点
    - 没有锚点时：用 focus 兜底 / 询问 / 进候选层

A2. 从流式文本抽候选 mention
    - 本地 NER/词典/LLM 候选
    - 这一步允许"什么都识别"，先不建节点

A3. 快速关系粗判（锚点 ↔ 候选）
    - 目标：筛掉明显无关，不追求最终正确
    - 可用：别名/embedding/共现/小分类器/轻量 LLM
    - 输出：possible / unrelated / defer
      - unrelated：明确无关（可暂不建）
      - possible：进 provisional
      - defer：候选层，等慢判

A4. provisional（临时节点）
    - 半透明/虚线，不写正式节点表（或 status=provisional）
    - 不出题、不参与三档、不参与副本、不计统计
    - 被 ASR 修订时直接替换

A5. 慢速 LLM 精准判定
    - 对 provisional 与锚点/其他已有节点做成对判定
    - 输出：谓词、方向、证据、置信度、unrelated
    - 要求证据；无法判断 → 不建正式关系

A6. commit 或修复
    - 通过：正式节点 + 正式/建议关系
    - 不通过：
      - 有更合适的已有节点 → 重连（relink）
      - 确认无关/重复 → 墓碑/软删除（不硬删）
      - 只是证据不足 → 保留 topic 节点，关系标"待确认"
    - 最多 2–3 轮，避免修复风暴

A7. 方向/推荐
    - commit 后生成探索方向
    - 与已有节点的推荐关联只做虚线建议，用户确认才正式
```

**证据状态：**

| 环节 | 证据 |
| --- | --- |
| 锚点/上下文增量扩展 | ✅ Graphiti/GraphRAG 有增量上下文思路 |
| 候选剪枝再给 LLM | ✅ DocRE 分类器+LLM（arXiv 2408.13889） |
| "无关"作为 veto | ⚠️ 间接（ACL 2024 证明"有关"有偏置），需校准 |
| provisional/ghost | ⚠️ 通用 optimistic UI，非 KG 项目证明 |
| 两阶段修复 | ❌ 系统设计推断，无 KG 开源实现 |
| 方向/推荐并行 | ⚠️ 产品推断，非现成管线 |

**主要风险：**

- 快速无关判断假阴性（该建没建）；
- 候选多、锚点多时配对爆炸；
- provisional 闪动/撤回成本；
- 修复级联复杂；
- "可删除"与基线"只隐藏"冲突。

**适合：** 锚点明确、用户学习顺序清晰、愿意接受 ghost 的实时场景。

---

### 10.2 方法 B：角色优先 + 关系判定

**一句话：** 先判断"这些词是什么角色"（学习对象/比喻/例子/步骤/噪声），只让学习对象进入关系判定；再用证据判关系。

**流程：**

```text
B1. 从流式文本抽候选 mention
    - 允许识别很多词，先不建节点

B2. 角色分类
    - topic（话题主体）
    - subconcept（理解主体必需）
    - process（过程/工作流本体）
    - example（举例）
    - metaphor（比喻/类比）
    - step（过程步骤）
    - noise（口头语/代词/玩笑）

B3. 角色分流
    - topic/subconcept/process → 候选节点
    - example/metaphor → 写进相关节点 MD（不建节点、不建正式关系）
    - step → 进流程副本（不建节点）
    - noise → 丢弃

B4. 关系判定（只对候选节点）
    - 与锚点/已有节点做成对判定
    - 输出：谓词、方向、证据、置信度、unrelated
    - 证据不足 → 建议/待确认/不建

B5. commit
    - 角色合格 + 关系有证据 → 正式节点 + 关系
    - 角色合格但关系未知 → topic 节点可先建、关系待确认（产品决策）
    - 角色不合格 → 不建节点

B6. 方向/推荐
    - 同方法 A：commit 后生成；推荐只做虚线建议
```

**证据状态：**

| 环节 | 证据 |
| --- | --- |
| 实体类型/schema 过滤 | ✅ GraphRAG/DeepKE/GLiREL 有类型/标签约束 |
| 关系判定/无关系类 | ✅ DocRE/GLiREL/RE 基准 |
| 候选先剪枝 | ✅ DocRE 分类器+LLM |
| 角色分类（metaphor/step 等） | ❌ 无现成 KG 项目；属于产品语义 |
| "角色优先于关系"的顺序 | ❌ 逻辑推断，未验证 |
| topic 节点无关系先建 | ❌ 产品决策，未验证 |

**主要风险：**

- 角色分类误判（把新概念判成 example/metaphor，或反过来）；
- 中文隐喻识别难；
- 多一次模型调用，延迟增加；
- 新主题可能被误杀；
- 角色分类的标签体系需要产品确认。

**适合：** 教学语义要求高、比喻/步骤/例子噪声多、可以多一次分类调用的场景。

---

### 10.3 两者的关键差异

| 维度 | A 锚点优先 | B 角色优先 |
| --- | --- | --- |
| 第一步 | 锚点 ↔ 候选关系粗判 | 候选角色分类 |
| 排除白雪公主等 | 靠"与锚点无关" | 靠"role=metaphor" |
| 关系判定次数 | 候选×锚点（可剪枝） | 只对 topic/subconcept/process |
| 新增模型调用 | 快筛（可本地）+ 慢判 | 角色分类 + 慢判 |
| 主要误判 | 无关假阴性、配对爆炸 | 角色误判、新主题误杀 |
| 教学语义 | 较弱（靠关系） | 较强（角色显式） |
| 实现复杂度 | 中（provisional/修复） | 中（角色体系） |
| 证据 | 组件有依据，流程未证明 | 组件有依据，角色层未证明 |

### 10.4 共同必须满足的约束

无论 A/B：

1. 不能先建正式节点再硬删；provisional/软删除；
2. 关系必须允许 `unrelated/unknown`；
3. 关系必须有证据；低置信不建正式；
4. 方向/推荐不能因为 provisional 就解锁副本；
5. 每片段节点/调用上限；
6. 旧结果不得覆盖新状态（taskId/graphVersion）。

### 10.5 实验设计（决定选 A 还是 B）

同一批 40 句（含白雪公主句、工作流句、普通学习句），人工标注：

- 应建节点、应排除词、角色、关系/无关、方向。

三组跑：

1. A：锚点优先；
2. B：角色优先；
3. C：A+B 混合（角色粗筛 + 锚点快判 + 慢判）。

指标：

- 节点误建率（metaphor/example/step）；
- 节点假阴性率；
- 关系 P/R、方向合法率、无关判断；
- 调用次数/P95 延迟；
- provisional→commit 转化率、修复率；
- 用户体感（ghost 闪动、等待）。

**实验前不把 A 或 B 写进需求基线；实验后再定。**
